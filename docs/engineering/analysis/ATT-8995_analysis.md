## 1. Problem Domain & Root Cause Analysis
- **Observed Defect**: When a cockpit tile enables both Value (`showValue = true`) and Graph (`showGraph = true`) — e.g. 5 stacked RR tiles in `Test RR` — the sparkline polyline is squashed into a tiny horizontal strip (~`11–12.dp` net amplitude) despite ample vertical space on screen.
- **Confirmed Code Root Causes**:
  1. **Insufficient Value+Graph Container Height (`SensorSparklineView.kt:55-70`)**: Originally (`ATT-1294`), `SensorSparklineView` rendered only a `Canvas` (`14/20/28/36.dp`). When `ATT-6695` (`ef243477`) added the single-line X-axis label `Row` (`-T  -T/2  Jetzt`) inside `SensorSparklineView`'s `Column` below `Canvas(Modifier.weight(1f))`, `resolveSparklineHeight(..., isGraphOnly = false)` increased only to `26 / 34 / 44 / 52.dp` (`XSMALL/SMALL`, `NORMAL`, `LARGE`, `XLARGE+`).
  2. **Inherited `16.sp` Label Leading + `6.dp` Canvas Padding (`SensorSparklineView.kt:211-212, 362-379`)**: `MaterialTheme.typography.labelSmall.copy(fontSize = 10.sp)` inherits M3 `lineHeight = 16.sp` (`~16.dp`), and `Canvas` deducts `2 * 3.dp = 6.dp` (`verticalPaddingPx`). Net curve drawing amplitude (`usableHeight`) collapses to **`4.dp`** (`XSMALL/SMALL`), **`12.dp`** (`NORMAL`), **`22.dp`** (`LARGE`), and **`30.dp`** (`XLARGE+`).
  3. **Rigid `.height(...)` in `SensorFieldView.kt:505-507`**: Value+Graph mode applies fixed `Modifier.height(resolveSparklineHeight(fieldState.viewSize, isGraphOnly = false))`, ignoring surplus vertical tile height (e.g. next to a taller neighbor in `Row(IntrinsicSize.Min)` at `SensorGridScreen.kt:749,1122`).

## 2. Independent Peer Review & Verification (4-Augen-Prinzip)
Auditing the ticket hypothesis directly against `sprint/2026-11-20_02_Spät` (`c62c42b3`) confirms all cited call sites and surfaces 4 design nuances:
1. **Tightening X-Axis `lineHeight = 12.sp` (`SensorSparklineView.kt:364,370,376`)**: `10.sp` numerals + `Jetzt`/`Now` carry `6.sp` dead leading under inherited `16.sp` `lineHeight`. Setting `lineHeight = 12.sp` reclaims `~4.dp` directly for the `Canvas` curve with zero glyph clipping.
2. **Flexible `.heightIn(min = ...).weight(1f)` vs Rigid `.height(...)` (`SensorFieldView.kt:505-507`)**: Using `Modifier.heightIn(min = resolveSparklineHeight(fieldState.viewSize, isGraphOnly = false)).weight(1f)` (mirroring Graph-only mode from `ATT-6689`) solves **three** cases simultaneously:
   - In `SensorGridScreen.kt:749,1122` (`Row(IntrinsicSize.Min)` inside `verticalScroll`), `heightIn(min = H)` floors `minIntrinsicHeight` so rows expand to give the sparkline `>= H` (`5 × ~148.dp = ~740.dp` for 5 stacked `NORMAL` tiles on a `~850–915.dp` viewport).
   - In multi-column rows alongside a taller tile, `.weight(1f)` claims surplus vertical height instead of leaving dead whitespace.
   - In externally constrained fixed-height tiles (e.g. `SensorFieldViewDynamicZoneScreenshotTest` `132.dp`/`116.dp` cards or Value+Bar+Graph tiles), `.weight(1f)` safely absorbs remaining height after Value + Bar without clipping the primary Value text or X-axis labels (whereas rigid `.height(52.dp)` would clip the bottom `16.dp` inside a `132.dp` card!).
3. **Graph-Only vs Value+Graph Monotonicity (`SensorSparklineView.kt:55-70`)**: Raising `isGraphOnly = false` to `46 / 52 / 60 / 68.dp` yields **`28 / 34 / 42 / 50.dp`** net Canvas height (squarely in the requested `28–36.dp` band at `NORMAL`, and still `24 / 30 / 38 / 46.dp` even under `16.dp` label height). Keeping `isGraphOnly = true` monotonically taller (`48 / 56 / 68 / 84.dp` -> `30 / 38 / 50 / 66.dp` net Canvas) ensures disabling `Value` in a single-tile `IntrinsicSize.Min` row never *shrinks* the sparkline!
4. **WYSIWYG Preview Parity (`EditSensorFieldDialog.kt:526`)**: Updating preview height `44.dp -> 52.dp` aligns the dialog preview 1:1 with `ViewSize.NORMAL` (`34.dp` net Canvas height).
