# Stage 1 Analysis — ATT-9600: Unify GNSS & IMU Timestamps onto Monotonic `elapsedRealtime` Clock

- **Ticket**: `ATT-9600` (`2 SP`, `Bug`, `tier-a`, Epic `ATT-166`) | **Target Release**: `V5.0.0` | **Risk Rating**: `HIGH`
- **Problem Statement**: Sidecar telemetry from Pixel 10 workout `2026-11-22_081402` (`Zum Bäcker #60`, `workoutID = 2428`) revealed a **`~2.18 s` clock-domain offset** between GPS `Location.getTime()` (`1795331657000`) and `System.currentTimeMillis()` (`1795331659182`) at matching monotonic `CLOCK_BOOTTIME` (`elapsedRealtimeNs = 685756090818846` vs `685756550030993`, `+459 ms`). Interleaving wall-clock IMU timestamps with lagging GNSS epoch timestamps causes `-2.18 s` backward timestamp sawtooths on every 1-Hz fix and immediate bypass of `PhoneCarriageClassifier.dismountHysteresisMs` (`2.0 s`), producing sub-second `0.77 s` / `1.03 s` `BIKE_FRONT_POCKET (4) <-> WALKING_TRANSITION (1)` mode chatter.

## 1. Independent Peer Review & Forensic Verification (4-Augen-Prinzip)

Code-grounded audit against live `sprint/2026-11-22_03_Nacht` (`25208596`) confirms the ticket's root cause and identifies **4 critical cross-cutting invariants** that a naive replacement would break:

1. **Dual Clock-Domain Split (`SpeedAndLocationDevice_ATTFused.kt`)**:
   - `resolveSensorEventTimestampMs()` (`L399-430`) aligns `SensorEvent.timestamp` (`CLOCK_BOOTTIME` ns) onto **wall-clock** `currentTimeMillis()`, while `onLocationChanged()` (`L512`) uses `location.time` (ignoring `location.elapsedRealtimeNanos`), and `mSportChangedReceiver` (`L165`), `onWheelMeasurement()` (`L766`), and `triggerDecayTick()` (`L1479`) use `currentTimeMillis()`.
   - When `onLocationChanged()` seeds `PhoneCarriageClassifier.candidateSinceMs = location.time` (`wallMs - 2,182 ms`), the next IMU callback `~450 ms` later evaluates `nowMs - candidateSinceMs = 2,632 ms >= 2,000 ms`, bypassing dwell hysteresis instantly.
2. **4-Augen Catch #1 — External Wall-Clock Boundaries (`L506`, `L747`, `L878`, `L1352`)**:
   - `evaluateMultisportTransitionIfDue()` (`L1340-1356`) feeds `MultisportTransitionBridge.evaluateAndDispatch()` -> `MultisportLapCoordinator.formatUtcTimestamp(anchor.timestampMs)` (`Laps.db` UTC `"yyyy-MM-dd HH:mm:ss"`). Passing monotonic uptime ms (`~6.85e8`) would corrupt `Laps.db` to `1970-01-08`! Instead, throttle on monotonic ms and map external `MultisportTelemetryAnchor.timestampMs` via monotonic-offset UTC epoch (`wallOrigin + (monoMs - monoOrigin)`, NTP-rewind immune).
   - `SmartphoneRawTelemetryRecorder.updateCarriageMode(mode.code, epochMs)` (`L878`), `recordLocation` (`L506`), and `recordWheel` (`L747`) MUST continue passing UTC wall-clock `epochMs` (the recorder already stamps `elapsed_realtime_ns` independently).
3. **4-Augen Catch #2 — Production Wheel Callbacks (`MySensorManager.java:266`)**:
   - `MySensorManager` invokes `onWheelMeasurement(speed, 0.05, System.currentTimeMillis())`. If GNSS/IMU move to `elapsedRealtime` (`< 1.5e12`) while wheel callbacks remain at Unix epoch (`~1.79e12`), `abs(timestampMs - lastWheelMs) <= 5000L` (`L536`) always fails and `carriageClassifier.ingestWheelSpeed()` prunes all IMU windows! Normalizing incoming wall-clock wheel timestamps (`>= 1.5e12`) onto `elapsedRealtime` inside `AttFusedTimestampNormalizer` unifies all 5 sensor streams with zero `MySensorManager.java` churn.
4. **4-Augen Catch #3 — Plain-JVM Unmocked `SystemClock` & Robolectric Frozen `SystemClock`**:
   - Plain-JVM tests (`returnDefaultValues = false`) throw on `SystemClock.elapsedRealtimeNanos()`, override `currentTimeMillis() = fakeClockMs`, and pass `location.elapsedRealtimeNanos == 0L` with `location.time = fakeClockMs`.
   - Robolectric (`SpeedAndLocationDevice_ATTFusedBANALServiceIntegrationTest.kt`) keeps `SystemClock.elapsedRealtimeNanos()` frozen at `100 ms` while advancing `fakeClockMs` (`1_000..15_980 ms`) and `Location.time = fakeClockMs` (`elapsedRealtimeNanos == 0L`). Re-anchoring must distinguish active platform clock progression (`refNowMs - alignedMs > 5 s` or `platformAdvanced && alignedMs - refNowMs > 5 s`) from a frozen Robolectric clock and preserve relative `< 1.5e12` test timestamps when `location.elapsedRealtimeNanos == 0L`.
5. **4-Augen Catch #4 — Defensive Out-of-Order Guards & Monolith Cap (`1,498 / 1,500` LoC)**:
   - Even on unified `CLOCK_BOOTTIME`, normal `~100–500 ms` GNSS pipeline latency can deliver `location.elapsedRealtimeNanos` slightly behind the newest 50-Hz IMU sample; `PhoneCarriageClassifier.classify(nowMs)` MUST clamp `effectiveNowMs = max(nowMs, lastEventTimestampMs)` so `candidateSinceMs` is never seeded in the past, and `UnicycleOdometryEkf` MUST keep `currentTimestampMs` non-decreasing.
   - `SpeedAndLocationDevice_ATTFused.kt` is at `1,498 / 1,500` LoC; extracting pure-Kotlin `AttFusedTimestampNormalizer.kt` shrinks it to `~1,475 / 1,500` LoC.
