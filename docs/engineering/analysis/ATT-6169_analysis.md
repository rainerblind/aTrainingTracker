## 1. Problem Statement & Motivation
In the independent ASPICE 4.0 pre-assessment of 2026-11-08, remediation item S-08 (ASPICE SYS.5: System Verification Base Practices, SUP.8: Configuration & Release Management) highlighted a critical governance gap in the release lifecycle of aTrainingTracker:
* Release decisions and release checklists in `.agents/skills/release-manager/SKILL.md` (and historical release tickets such as ATT-170 and ATT-1191) only verified unit-level/APK-level build artifacts (`app-release.aab`, `app-release.apk`, `apksigner` output).
* They completely lacked references to system-level evidence:
  1. **SYS.4 System Integration Verification results**: The output of the automated system integration runner (`docs/releases/<tag>/system_integration_results.json` generated by `tools/run_system_integration_tests.py` per ATT-6166).
  2. **SYS.5 System Verification Protocol sign-off records**: The executed and signed-off formal protocol on target hardware/environmental conditions (`docs/releases/<tag>/sys_verification_record.md` per ATT-6167).
* Without explicit gates requiring verified system integration and system verification evidence before release candidate tag creation, release candidate builds could theoretically be tagged and distributed without proving end-to-end system compliance against `SYSREQ-TRK-*` and `SYSREQ-DEX-*` requirements.

The goal of ATT-6169 is to eliminate this gap by embedding mandatory SYS.4 and SYS.5 evidence gates into the release manager workflow, updating release templates, providing an automated contract test, and updating living documentation with 100% traceability.

## 2. Root Cause Analysis & Independent Hypothesis Verification (ATT-5431)
1. **Historical Focus on Unit & Build-Level Sign-Off (SUP.8 Gap)**:
   - The original release checklist in ATT-170 focused on GitFlow branching, Gradle compilation, signing keystores, and Play Store upload.
   - Because ASPICE SYS.4 (virtual integration) and SYS.5 (on-device verification) were only recently established under tickets ATT-6166 and ATT-6167, the release-manager skill was never updated to enforce them as blocking prerequisites.
2. **Missing Prerequisite Gate Before Tagging**:
   - In GitFlow, creating a release tag (`V<versionName>__<versionCode>`) marks a release candidate milestone. If system verification is performed after tagging, any detected system regressions invalidate the tag, forcing messy tag deletions or unversioned re-builds.
   - Therefore, system verification evidence must be verified **prior to tagging** (during Phase 1/Phase 2 preparation and release candidate approval).
3. **Artifact Repository Standardization (`docs/releases/<tag>/`)**:
   - ATT-6166 established `docs/releases/<tag>/system_integration_results.json`.
   - ATT-6167 established `docs/releases/<tag>/sys_verification_record.md`.
   - A standardized release documentation folder structure and template (`docs/releases/README.md`, `docs/releases/TEMPLATE.md`) is needed so release managers know the exact schema, required artifacts, and sign-off criteria.

## 3. User Scope Grounding (ATT-1250)
* **In-Scope Goals**:
  1. Update `.agents/skills/release-manager/SKILL.md`:
     - Embed mandatory gates for system evidence:
       * SYS.4 System Integration Verification (`docs/releases/<tag>/system_integration_results.json` from `tools/run_system_integration_tests.py`).
       * SYS.5 System Verification Protocol sign-off (`docs/releases/<tag>/sys_verification_record.md` per `docs/system/sys_verification_protocol.md`).
     - Update the release checklist and step-by-step procedures to explicitly block release candidate tag creation (`V<versionName>__<versionCode>`) and Play Store distribution if either record is missing or contains failing test verdicts.
     - Add explicit commands and instructions for running the automated integration runner and verifying the protocol record.
  2. Create `docs/releases/` governance and template assets:
     - `docs/releases/README.md`: Explaining the release directory architecture, required artifacts, and SYS.4/SYS.5 release gates.
     - `docs/releases/TEMPLATE.md`: Reusable release dossier template referencing SYS.4 and SYS.5 sign-off criteria.
  3. Update `docs/architecture.md`: Reference release governance integration and SYS.4 / SYS.5 evidence gating in Section 6.
  4. Implement JUnit Contract Test `ReleaseManagerSystemEvidenceContractTest.kt` in `app/src/test/java/com/atrainingtracker/trainingtracker/build/`:
     - Verify `.agents/skills/release-manager/SKILL.md` contains mandatory gates for SYS.4 and SYS.5.
     - Verify blocking rule on release candidate tag creation.
     - Verify `docs/releases/` directory and template files exist and contain required sign-off criteria.
  5. Register living documentation entries `REQ-PRO-072` and `TST-PRO-072` in `docs/requirements/req_process_stability.md` and `docs/tests/tst_process_stability.md` with 100% master index parity.
* **Out-of-Scope Non-Goals**:
  - No changes to Android production runtime code in `app/src/main/`.
  - No alteration of existing keystore signing logic or Gradle build scripts.
