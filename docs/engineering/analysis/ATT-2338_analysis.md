## 1. Problem Statement & User Value Proposition

When importing a workout file recorded on modern GPS bike computers or sports watches (Garmin Edge, Wahoo ELEMNT, Hammerhead Karoo, Coros) in Garmin FIT binary format (`.fit`) via the Import & Backup tab, the imported workout contains zero elevation data:
- The elevation profile chart in `TrackOnMapScreen` / `WorkoutDetailsScreen` is missing or flat.
- The summary statistics display `0 m` total ascent and `0 m` total descent.
- Elevation-based telemetry analysis and 3D route clustering are completely disabled.

### Identified Pain Points & Friction:
1. **Loss of Critical Elevation Telemetry**:
   - In modern Garmin FIT SDK specification profiles (FIT profile 21.x+), altitude is encoded in field `78` (`enhanced_altitude` / `getEnhancedAltitude()`) rather than the legacy field `2` (`altitude` / `getAltitude()`).
   - `LegacyImportEngine.kt` currently only inspects `record.altitude`, causing modern recordings where field 2 is omitted or invalid to be treated as having no altitude samples.
2. **Missing Enhanced Speed & Summary Metric Fallbacks**:
   - Similarly, modern FIT recordings provide high-resolution speed in field `73` (`enhanced_speed` / `getEnhancedSpeed()`) rather than legacy field `6` (`speed` / `getSpeed()`), which can lead to truncated or missing speed samples if legacy speed is omitted.
   - FIT files also contain official summary ascent and descent metrics in `SessionMesg` (`totalAscent` [field 22], `totalDescent` [field 23], `totalFractionalAscent` [field 199], `totalFractionalDescent` [field 200]). If sample-level elevation is absent or flat, these session totals should serve as authoritative reference metrics.

Fixing this parsing gap ensures that modern FIT workouts imported into aTrainingTracker retain complete elevation profiles, accurate total elevation gain/loss, and high-fidelity speed curves.

## 2. Root Cause Analysis (Forensic Investigation & Architecture Gaps)

1. **`LegacyImportEngine.kt` FIT Record Parsing**:
   In `importFromFitResult` (lines 1356–1371):
   ```kotlin
   record.altitude?.toDouble()?.let { alt ->
       if (alt < minAltVal) {
           minAltVal = alt
           minAltPos = pos
       }
       if (alt > maxAltVal) {
           maxAltVal = alt
           maxAltPos = pos
       }
   }

   record.altitude?.toDouble()?.let { alt ->
       values.put(SensorType.ALTITUDE.name, alt)
       altitudes.add(alt)
   }
   ```
   and speed (line 1378):
   ```kotlin
   record.speed?.toDouble()?.let { spd ->
       values.put(SensorType.SPEED_mps.name, spd)
   }
   ```
   - In Garmin FIT SDK (`com.garmin.fit.RecordMesg`):
     - `getAltitude()` reads field 2 (16-bit uint with scale/offset, max 9,000m).
     - `getEnhancedAltitude()` reads field 78 (32-bit uint with scale/offset, supporting high-altitude flight and high precision).
     - Modern devices often only populate `enhanced_altitude` and omit `altitude`, or set `altitude` to an invalid marker.
     - Because `LegacyImportEngine` exclusively checks `record.altitude`, `altitudes` remains empty!
2. **Consequences on Downstream Post-Processing (`recalculateStats`)**:
   - `minAltVal` and `maxAltVal` remain uninitialized (`Double.MAX_VALUE`, `-Double.MAX_VALUE`).
   - `minAltPos` and `maxAltPos` remain `null`.
   - `altitudes` list passed to `recalculateStats` has size 0.
   - `recalculateStats` sets `WorkoutSummaries.ALTITUDE_ASCENT = 0`, `ALTITUDE_DESCENT = 0`, `ALTITUDE_MIN = 0`, `ALTITUDE_MAX = 0`.
   - `WorkoutSamples` database contains zero rows with `SensorType.ALTITUDE`.
   - When the user opens the workout in `TrackOnMapScreen`, the elevation profile chart cannot render.

## 3. Scope & Chesterton's Fence Archaeology

### Chesterton's Fence Audit:
1. **Why was `record.altitude` originally used?**:
   - The initial FIT import implementation in `ATT-1117` focused on basic field mapping from the standard SDK messages. `record.altitude` was the most obvious getter on `RecordMesg`.
2. **What invariants must be preserved?**:
   - **Legacy FIT Compatibility**: Older FIT files generated by legacy devices that only populate `record.altitude` must continue to parse without disruption.
   - **Enhanced Precedence**: If both `enhancedAltitude` and `altitude` are present, `enhancedAltitude` should take precedence due to its higher precision and larger range.
   - **Out-of-Range Guard**: Altitude values must be filtered for physical plausibility (e.g. FIT invalid sentinels like `0xFFFFFFFF` or out-of-range altitudes outside `-500m .. 9000m`).
   - **Speed Compatibility**: Similarly, `record.enhancedSpeed ?: record.speed` must be adopted with non-negative validation (`spd >= 0.0`).
   - **Session Ascent/Descent Reference**: `SessionMesg` total ascent and descent should be captured and utilized if sample-level elevation is flat or empty.

## 4. Technical Architecture & Implementation Design

### 1. `RecordMesg` Elevation & Speed Extraction Helper:
In `LegacyImportEngine.kt`, extract altitude and speed with robust fallback:
```kotlin
val altVal = (record.enhancedAltitude ?: record.altitude)?.toDouble()
val spdVal = (record.enhancedSpeed ?: record.speed)?.toDouble()
```
Include boundary sanity checks:
```kotlin
if (altVal != null && altVal in -500.0..10000.0) {
    if (latSemi != null && lngSemi != null && latSemi != 0x7FFFFFFF && lngSemi != 0x7FFFFFFF) {
        if (altVal < minAltVal) {
            minAltVal = altVal
            minAltPos = pos
        }
        if (altVal > maxAltVal) {
            maxAltVal = altVal
            maxAltPos = pos
        }
    }
    values.put(SensorType.ALTITUDE.name, altVal)
    altitudes.add(altVal)
}

if (spdVal != null && spdVal >= 0.0 && spdVal <= 100.0) {
    values.put(SensorType.SPEED_mps.name, spdVal)
}
```

### 2. `LapMesg` & `SessionMesg` Enhanced Speed & Summary Support:
In `rawLaps.forEachIndexed`:
```kotlin
val lapMaxSpeed = (lapMesg.enhancedMaxSpeed ?: lapMesg.maxSpeed)?.toDouble()
```
In `rawSessions`:
Extract `sessionMesg.totalAscent` and `sessionMesg.totalDescent` to pass or verify against `recalculateStats`.
