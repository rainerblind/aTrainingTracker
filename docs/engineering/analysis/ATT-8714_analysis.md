# Stage 1 Analysis: ATT-8714 - Polar Live-IMU-Streaming Toggle & HR/Raw-Telemetry Continuity

**DOC-ID**: `DOC-ANA-ATT-8714` | **Ticket**: `ATT-8714` (`3 SP`, `severity-major`, Parent `ATT-5910`) | **Target Release**: `V5.0.0` | **Sprint**: `2026-11-18_01_Früh` | **Branch**: `feature/ATT-8714` | **Date**: `2026-11-18`

## 1. Problem Statement & Motivation
* On Pixel 10 with Polar Verity Sense (`24:AC:AC:24:82:56`) and Polar H10 (`24:AC:AC:25:0F:A6`), enabling *Live-IMU-Streaming* (`polarLiveImuEnabled = true`) while the Polar sensor is already connected causes `HR` delivery to stop/fail on transition, and `files/raw_sensor/` remains empty on Polar Verity Sense.
* Expected: Toggling `polarLiveImuEnabled` (on/off, pre-workout or while connected) cleanly transitions between `BTLEHeartRateDevice` and `PolarOnlineStreamingBridge` without dropping `HR`/`RR_INTERVAL`, and reliably delivers live `HR`, `ACC`, `GYRO` (Verity Sense), and `files/raw_sensor/*.polar_raw.csv.gz` sidecars.

## 2. Root Cause Analysis & Independent Hypothesis Verification
* **Root Cause #1 — Missing Live Handoff & Async GATT Teardown Race (`EditDeviceDialog` -> `DeviceDataRepository` -> `DeviceManager`)**:
  * `EditDeviceViewModel.saveChanges()` (`:362-368`) delegates to `DeviceDataRepository.updateDevice()` (`:360-434`), which updates `POLAR_LIVE_IMU_ENABLED` in `Devices.db` (`:512-514`) and emits broadcasts ONLY for `wheelCircumference` and `isPaired` (`:424-432`)—emitting zero signal when `polarLiveImuEnabled` changes.
  * `DeviceManager.mMyRemoteDevices` retains the active `BTLEHeartRateDevice` (or `PolarOnlineStreamingBridge`); both `createNewBluetoothLEDevice()` (`:1378`) and `createPairedRemoteDevices()` (`:1479`) skip existing `deviceID` entries.
  * Even when a device is stopped and recreated (`removeAndStopRemoteDevice()` `:1295-1307`), `MyBTLEDevice.disconnectFromGatt()` (`:828-842`) posts `gattToClose.disconnect(); gattToClose.close()` asynchronously to `mHandler`, and `PolarOnlineStreamingBridge.shutDown()` (`:864`) disconnects asynchronously in `BDBleApiImpl`. Starting the replacement connection before GATT closes starves Polar SDK discovery (`BDBleApiImpl$connectToDevice` scans for connectable advertisements suppressed by the open GATT link, especially on Verity Sense) or drops `HR` via `SEARCH_PERIOD` timeout.
* **Root Cause #2 — Status on `9f9e5967` (`ATT-8690` + `ATT-8717`) vs. Remaining `PolarOnlineStreamingBridge` Gaps**:
  * **Already Solved (`ATT-8690` `34b78941`, `ATT-8717` `9f9e5967`)**: `PolarOfflineGattCoordinator` (`:73-352`) now centralizes the 8-feature `PolarBleApi` singleton with ref-counting (no sibling `cleanup()`), global `multiplexerCallback`, bidirectional `MAC <-> 8-hex` `deviceAliases` (`:111-156`), and DIS `0x2A24`/`0x2A25` + PMD/PFTP persistence (`BTLEHeartRateDevice.java:113-153`, `PolarOfflineCapabilityStore.kt:166-226`). `bleSdkFeatureReady` (`PolarOnlineStreamingBridge.kt:325-329`) already uses `matchesDeviceIdentifier`.
  * **Still Broken on `9f9e5967`**:
    1. *Already-Open Shared Session / Already-Ready Features*: `BDBleApiImpl.connectToDevice()` returns immediately without re-emitting `deviceConnected` or `bleSdkFeatureReady` if the session is already `SESSION_OPEN` on the shared `PolarBleApi` (e.g., from offline arming/sync). `PolarOnlineStreamingBridge.connectPersistentSession()` (`:440-460`) never checks `api.isFeatureReady(...)` or syncs an already-open session, leaving `isConnectedFlag = false` and `startHrCollection()`/`startImuCollection()` uninvoked.
    2. *Mid-Session `polarId` Getter Mutation*: `PolarOnlineStreamingBridge.polarId` (`:203-204`) is dynamically computed; if a renamed sensor connects by `macAddress` before `deviceConnected` caches the 8-hex `deviceId` (`:289`), `polarId` flips mid-session to 8-hex. Because `PolarServiceClientUtils.sessionByDeviceId` matches `advertisementContent.polarDeviceId` (empty when opened directly by MAC), `startHrStreaming(polarId)`/`requestStreamSettings(polarId)` can fail silently in `.catch {}` (`:468, 533, 555`) unless falling back to `macAddress` or keeping the resolved SDK session identifier consistent.
    3. *Disconnect/Reconnect Job Hygiene*: `deviceDisconnected` (`:307-319`) does not cancel stale `hrJob`/`accJob`/`gyroJob` before auto-reconnect.
* **Root Cause #3 — Why `files/raw_sensor/` Remained Empty on Verity Sense**:
  * `TrackerService.java:1266` starts `PolarRawTelemetryRecorder.startActiveSession()`, which attaches strictly to `PolarOnlineStreamingBridge.activeBridges` (`PolarRawTelemetryRecorder.kt:358`, `PolarOnlineStreamingBridge.kt:114, 299`). While `BTLEHeartRateDevice` stayed active (Cause #1) or the bridge failed to enter `deviceConnected` + `FEATURE_HR`/`FEATURE_POLAR_ONLINE_STREAMING` (Cause #2), `rowCount == 0` triggered `tempFile.delete()` in `finalizeFile()` (`PolarRawTelemetryRecorder.kt:145-150`).

## 3. Scope Grounding & Non-Goals (`ATT-1250`)
* **In-Scope (`3 SP`)**: (1) Broadcast/dispatch a dedicated `polarLiveImuEnabled` change signal from `DeviceDataRepository.updateDevice()` to `DeviceManager` (`BANALService` constant + receiver) to cleanly tear down the old HRM device (`BTLEHeartRateDevice` <-> `PolarOnlineStreamingBridge`), allow GATT release before opening the replacement, recreate via `createRemoteDevice()`, and trigger reconnect/search + `RrBeatSource` / `FilterManager` / `PolarRawTelemetryRecorder` re-attachment; (2) Harden `PolarOnlineStreamingBridge` for already-ready/already-open shared `PolarBleApi` sessions, `macAddress` fallback if 8-hex SDK session lookup fails, and job cleanup in `deviceDisconnected`; (3) Unit/Robolectric tests covering live toggle handoff, GATT-yield ordering, already-ready HR/IMU startup, and `PolarRawTelemetryRecorder` sidecar capture (`N/A - no UI strings`).
* **Out-of-Scope**: `Devices.db` schema migration, Polar SDK upgrade, UI layout changes, physical Pixel 10 execution (deferred per `Rule 7.6`).
