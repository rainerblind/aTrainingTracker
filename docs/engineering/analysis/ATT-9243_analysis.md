# Stage 1 Analysis: ATT-9243 — Stop Never-Connected Paired BLE Devices From Triggering Aggressive Scan-Assist Reconnect Storms During Active Workouts

## 1. Problem Statement & Field Evidence
Logcat from Pixel 10 ride `Zum Bäcker #59` (`2026-11-20 05:59:02..06:08:33`, `PID 25651`) recorded **`54` instances** of `W/MyBTLEDevice: Scan assist throttled by Android scan quota (>= 4 scans in 30s); skipping scan` preceded by rapid `1s -> 2s -> 4s` retries logging `I/MyBTLEDevice: Search timed out for session-connected or active-workout device: persisting reconnect`. Riding without paired BLE sensors (HRM / Power / Radar left at home) caused absent never-connected devices to saturate Android's OS-wide 5-scans-per-30s quota, wasting battery and starving legitimate BLE scan-assist recovery.

## 3. Architectural Strategy & Scope Grounding (`ATT-1250`)
* **In-Scope**:
  1. **Distinguish Session-Connected vs. Never-Connected on Search Timeout (`MyBTLEDevice.java:472-525`)**: Preserve `isMidSessionOrWorkoutActive()` symbol (`DetailedDesignParityContractTest:198`), but split `mSearchTimeoutRunnable`: (a) `mHasConnectedInSession == true` persists fast `mReconnectRunnable` (`1s..16s..finalPeriodMs`) + `autoConnect = true` + queue release; (b) `!mHasConnectedInSession && isMidSessionOrWorkoutActive()` transitions `mState = DISCONNECTED`, sets `mIsBackgroundReconnecting = true`, keeps passive OS-managed `connectGatt(dev, true)` (`0` active scans), cancels/does **NOT** schedule `mReconnectRunnable`, and releases `DeviceManager` queue via `notifyStopSearching(false)`; (c) `!isMidSessionOrWorkoutActive()` (`READY` startup) preserves existing `disconnectFromGatt()` + `notifyStopSearching(false)`.
  2. **Gate Background Scan-Assist on `mHasConnectedInSession` (`MyBTLEDevice.java:831-868, 605-623`)**: Parameterize `initiateScanAndConnect(boolean allowScanAssist)` so `startSearching()` passes `true` (bounded single initial scan) while `attemptBackgroundReconnect()` passes `mHasConnectedInSession` (active scan-assist strictly for session-connected drops; passive `autoConnect = true` without scan-assist or `5s` timeout churn for never-connected devices). In `onConnectionStateChange(STATE_DISCONNECTED)`, floor reconnect delay at `>= 60_000 ms` when `!mHasConnectedInSession && isMidSessionOrWorkoutActive()`.
  3. **Skip Redundant Queue Re-Enqueues for Keep-Alive Devices (`DeviceSearchPeriodicRetryCoordinator.kt:95-127`)**: When `!success && current.shouldKeepAliveOnSearchTimeout()`, remove `current` from `deviceTries` without re-enqueueing for tries `2..N` (already handed off to passive `autoConnect = true` or decoupled background reconnect), reducing 3 absent BLE sensors from `9` sequential scans to `3` (`0` quota throttles) with `0` LoC added to `DeviceManager.java` (`1,707 / 1,708` LoC!).
  4. **Update Detailed Design & Refined Test**: Sync `docs/architecture/detailed_design/my_btle_device.md` and refine `BLEReconnectRobustnessTest.kt:484-518` (`TST-CON-051.1`) to reflect passive `autoConnect = true` without `mReconnectRunnable` for never-connected devices vs. fast `mReconnectRunnable` + scan-assist for session-connected devices.
* **Out-of-Scope**: `PolarOnlineStreamingBridge.kt` (`1,492/1,500` LoC), `MyANTDevice`, UI/Settings screens or string resources, SQLite schemas, or changing `MAX_RECONNECT_DELAY_MS = 16000L` / `MAX_SCANS_IN_WINDOW = 4`.

## 4. Chesterton's Fence Archaeology (`REQ-PRO-022`)
* **Original Requirement ID & Target**: `REQ-CON-036.1`/`.2`/`.3` (`ATT-7755`), `REQ-CON-051.1`/`.2` (`ATT-8998`), and `REQ-CON-052.1`/`.2` (`ATT-8965`) targeting `MyBTLEDevice.java`, `DeviceSearchPeriodicRetryCoordinator.kt`, `DeviceManager.java`, and `docs/architecture/detailed_design/my_btle_device.md`.
* **Historical Origin & Commit Trace**: `3dc19303` (`ATT-7755`) introduced `mHasConnectedInSession` and `isMidSessionOrWorkoutActive()` to prevent LSTO mid-workout drops from abandoning reconnect; `d2209175` (`ATT-8998`) added `mIsBackgroundReconnecting` and `shouldKeepAliveOnSearchTimeout()` to stop search-queue deadlocks; `6bb37af4` (`ATT-8965`) added `SensorReconnectBackoffPolicy` & `DeviceSearchPeriodicRetryCoordinator`; `f7ed7d94` (`ATT-9155`) added `triggerSilentConnectionReconnect()`.
* **Root Reason for Existing Formulation**: `ATT-7755` included `TrackingMode.TRACKING || PAUSED` inside `isMidSessionOrWorkoutActive()` so sensors turned on mid-ride could still connect without a manual re-search, and `ATT-8998` preserved that branch verbatim when unblocking `mSearchQueue`—unintentionally subjecting never-connected absent sensors to the same aggressive `1s -> 2s -> 4s` active scan-assist loop meant for dropped session-connected sensors.
* **Preservation of Core Invariants**: (1) Mid-workout disconnect of a session-connected sensor (`mHasConnectedInSession == true`) retains `1s -> 2s -> 4s -> 8s -> 16s -> ...` backoff + active `startScanAssistance()` + `autoConnect = true` (`REQ-CON-036`, `REQ-CON-052`); (2) never-connected active-workout sensors retain passive OS-managed `autoConnect = true` so mid-ride wake-up still auto-connects (zero active scans) and `mSearchQueue` never deadlocks (`REQ-CON-051.1`); (3) `READY`-mode offline startup battery bounding (`shutDown()` when periodic re-search disabled; `32s..finalPeriodMs` when enabled) is 100% preserved; (4) `ATT-9155` `triggerSilentConnectionReconnect()` & `PolarOfflineGattCoordinator` `pauseGattOperations()`/`resumeGattOperations()` preserved; (5) `MyBTLEDevice.MAX_RECONNECT_DELAY_MS == 16000L`, `DetailedDesignParityContractTest` symbols (`isMidSessionOrWorkoutActive`, etc.), and `DeviceManager.java <= 1,708` LoC preserved.
