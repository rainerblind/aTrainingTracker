## 1. Problem Statement & Motivation
* Post-workout ERTS recomputation (`ErtsPostWorkoutRecomputer` + `ExtendedRtsOdometrySmoother`) on Pixel 10 ride `Zum Bäcker #58` (`workoutID = 2411`, `584 s`) exhibits three coupled accuracy defects:
  1. `TIME_TOTAL` 1-Hz clock-beat `{1: 427, 2: 78, 0: 78}` pairs stretch the reconstructed ERTS timeline by `+78 s` (`~662 s` vs. `584 s`).
  2. `WorkoutSummaries.speedAverage_mps` and `ExtremumValues(SPEED_mps, AVG)` compute an unweighted sample mean (`3.050 m/s`) that disagrees by `7%` with `distanceTotal_m / timeActive_s` (`3.271 m/s`) and `Laps.db` (`3.265 m/s`).
  3. During a `118 s` indoor bakery stop (`speed = 0.00 m/s`, `acc = 48.5 m > MAX_GNSS_ACCURACY_METERS = 20 m`), ERTS clamps `speedMps = 0.0` and `deltaDistanceMeters = 0.0` yet allows smoothed `LATITUDE`/`LONGITUDE` to drift `35.66 m` across the building (`Haversine = 2,011.40 m` vs. `DISTANCE_m = 1,910.08 m`).
* **Expected**: 1-Hz timestamp reconstruction resists `TIME_TOTAL` `0/2` beat pairs while preserving genuine `> 5 s` pauses; `WorkoutSummaries.speedAverage_mps` and `ExtremaType.AVG(SPEED_mps)` equal `totalDistance / activeDurationSec` in parity with `TrackerService` & `Laps.db`; and stationary indoor epochs stay coordinate-pinned (`0.00 m` Haversine drift).

## 2. Root Cause Analysis & Independent Hypothesis Verification
* **Verified Root Causes on `sprint/2026-11-19_02_Spät` (`574ae3b5`)**:
  1. **`TIME_TOTAL` Clock-Beat Ratcheting (`ErtsPostWorkoutRecomputer.kt:271-305`)**: `ClockDevice` (`ClockDevice.java:141`) and `TrackerService` (`TrackerService.java:1358`) run asynchronous 1-Hz timers, causing `TIME_TOTAL` step beats `{0, 1, 2}`. Whenever a `+2 s` skip precedes a `0 s` duplicate (or separated `2 ... 0` beat pair), line `279` steps `ts` by `+2 s` (`candidateReconstructed`), line `296` advances `prevTs` by `+1 s` on the `dt = 0` row (`else` branch because `timeTotalSec > prevTimeTotalSec` is `false`), and the next `+1 s` row triggers `effectiveReconstructed > candidateReconstructed` (lines `288-291`), **permanently ratcheting `baseEpochMs` forward by `+1 s` per pair** (`78` pairs = `+78 s` stretch -> `662 s`, also inflating `deltaDist = v * dt` on stretched moving steps).
  2. **Unweighted Sample Mean `speedAverage_mps` Desync (`ErtsPostWorkoutRecomputer.kt:704, 750`)**: Both `updateWorkoutSummaries()` (`:704`) and `updateExtrema()` (`:750`) write `smoothedOdometry.map { it.speedMps }.average()` instead of authoritative `totalDistance / activeDurationSec`, violating `TrackerService.getAverageSpeed()` (`TrackerService.java:2687-2689, 2766-2775, 3129-3135`, `SCRUM-108`) and `LapsDatabaseManager.syncLapDistancesAndSpeeds()` (`LapsDatabaseManager.java:515`).
  3. **Stationary Indoor Covariance Blow-Up & Unpinned Backward RTS (`UnicycleOdometryEkf.kt:202-251, 355` & `ExtendedRtsOdometrySmoother.kt:216-272, 372`)**:
     * In forward replay (`ExtendedRtsOdometrySmoother.kt:372`), `ekf.predict()` runs with moving Jacobian `F[0][2] = cosMid*dt`, `F[1][2] = sinMid*dt` and `Q_POS = 0.01 m^2/s` even when `isStationary == true`. Because `applyZeroVelocityUpdate()` (`UnicycleOdometryEkf.kt:355`) sets `p[2][2] = max(p[2][2], ZUPT_SPEED_VARIANCE = 2.0)`, `F * P * F^T` injects `~2.0 m^2/s` (**200x `Q_POS`**) into `P[0][0] + P[1][1]` every stationary second (`~240 m^2` over `118 s`!).
     * When post-stop outdoor GNSS re-acquires (`acc <= 20 m`), the backward RTS pass (`smoothSnapshots()` `:216-272`) sees huge stationary `P_pos` and `C_k[0..1, 0..1] < I`, smearing the departure displacement (`~35.66 m`) smoothly backward across all `118` stationary seconds even though `smoothedStates[k][2]` is clamped to `0.0`.
* **Independent Peer Review & Verification (4-Augen-Prinzip Blind Spots & Monolith Ceilings)**:
  * **Blind Spot 1 (`2 -> 0` Ratchet & Pause/Stall Guard)**: Ticket description attributed ratcheting directly to `dt = 0` rows; live trace proves the ratchet occurs specifically on the *next* `timeTotalSec > prevTimeTotalSec` row after a `2 ... 0` beat pair via lines `288-291`. Anchoring active 1-Hz progression (`oneHzTs = prevTs + 1000L`) and re-anchoring strictly on genuine `> 5_000L ms` pauses (either `(parsedTs - oneHzTs) > 5_000L` or `(timeTotalTs - oneHzTs) > 5_000L`, never ratcheting on `0/2` beats) eliminates `+78 s` stretching across all `0/2` orderings while preserving `TST-FIL-027.1` (`6 s` SQLite batch-flush stall immunity + `30 s`/`25 s` double pauses).
  * **Blind Spot 2 (`TIME_ACTIVE_s` Null/Zero Fallback)**: `WorkoutSummariesDatabaseManager.getInt(workoutId, WorkoutSummaries.TIME_ACTIVE_s)` (`:785-802`) returns `0` when `TIME_ACTIVE_s` is `NULL` (as in `ErtsPostWorkoutRecomputerTest.createWorkout` which only seeds `TIME_TOTAL_s = 60` on 30–60 row fixtures). Fallback order MUST be: `TIME_ACTIVE_s > 0` -> integrated active `dt` (`sum(dt in (0, 5.0])` across `smoothedOdometry`) -> `speeds.average()`, unified across both `WorkoutSummaries.SPEED_AVERAGE_mps` and `ExtremaType.AVG(SPEED_mps)`.
  * **Blind Spot 3 (Forward `F * P * F^T` 200x Blow-Up)**: Zeroing `Q_POS` alone is insufficient because `F[0..1, 2] * P[2][2]` still adds `2.0 m^2/s`. Adding `@JvmOverloads` `isStationary: Boolean = false` to `UnicycleOdometryEkf.predict()` to freeze `x[0..1]`, set `F[0..1, :] = [I_2, 0]`, and zero `Q_POS` (preserving live `SpeedAndLocationDevice_ATTFused` caller unchanged and keeping `P_{k+1|k}` positive-definite/invertible) makes exact block RTS gain `C_k[0..1, :] = [I_2, 0]`; pairing this with explicit `smoothedStates[k][0..1] = smoothedStates[k + 1][0..1]` for `currStationary && nextStationary` in `smoothSnapshots()` guarantees `0.00 m` Haversine drift even for direct `smoothSnapshots()` callers and outdoor stationary GPS jitter.
  * **Monolith LoC Headroom Audit (`ArchitectureConformanceContractTest.kt:116-134`)**: All 3 touched production files are far below the `1,500` LoC threshold (`ErtsPostWorkoutRecomputer.kt`: `956 / 1,500`, `544` headroom; `ExtendedRtsOdometrySmoother.kt`: `737 / 1,500`, `763` headroom; `UnicycleOdometryEkf.kt`: `799 / 1,500`, `701` headroom). Protected monoliths remain **0 LoC touched**: `TrackerService.java` (`3,538 / 3,559`), `WorkoutSummariesDatabaseManager.java` (`3,148 / 3,148`), `WorkoutSamplesDatabaseManager.java` (`1,533 / 1,533`), `SpeedAndLocationDevice_ATTFused.kt` (`1,441 / 1,500`), `WorkoutRepository.kt` (`<= 5,117`), `DeviceManager.java` (`1,708 / 1,708`), `LapsDatabaseManager.java` (`612 / 1,500`).
