## 1. Problem Statement & Motivation

During the independent whole-app architecture review (`0234bfc0`), critical flaws were discovered in the Strava upload pipeline (`StravaUploader.kt`) and its supporting SQLite persistence helper (`StravaUploadDbHelper.java`):

1. **HTTP Error Code Misclassification & Lack of Retry on Transient Errors**:
   - `StravaUploader.kt:261-264`: Any HTTP response code other than 200 or 201 during the initial file upload is treated as a permanent failure:
     ```kotlin
     if (responseCode != 201 && responseCode != 200) {
         Log.w(TAG, "Bad response code from Strava: $responseCode")
         return ExportResult(false, false, "API Error: $responseBody") // retry = false
     }
     ```
   - Rate limit responses (`429 Too Many Requests`), server errors (`500 Internal Server Error`, `502 Bad Gateway`, `503 Service Unavailable`, `504 Gateway Timeout`), and short network anomalies return `retry = false`. As a consequence, `ExportWorker` / `ExportManager` permanently marks the workout export as failed instead of scheduling backoff retry.
   - Strava rate limits provide headers `X-RateLimit-Limit` and `X-RateLimit-Usage` which are completely ignored.
   - For `401 Unauthorized`, token expiration or invalidation during upload is treated as permanent error without an attempt to re-check or refresh the token.

2. **Fragile Polling Failure Tolerance**:
   - In `StravaUploader.kt:294-299`, during upload status polling (`getStravaUploadStatus`), if a single polling attempt fails due to a transient network glitch, returning `uploadStatusJsonAnswer == null`:
     ```kotlin
     if (uploadStatusJsonAnswer == null) {
         Log.w(TAG, "Attempt $attempt: getStravaUploadStatus returned null for uploadId=$uploadId")
         exportResult = ExportResult(false, false,"no correct response from Strava") // do not retry
         continue
     }
     ```
   - The loop immediately assigns `exportResult = ExportResult(false, false, ...)` and the outer loop terminates, abandoning the upload even if Strava accepted the file and is actively processing it, or would succeed on the next poll attempt.

3. **Pre-Upload Duplicate Discovery Defect & Activity Mis-Association**:
   - In `StravaUploader.kt:762-790`, `findExistingStravaActivity` searches a $\pm 300\text{ s}$ temporal window around `startEpochSeconds`.
   - Bug 1: `parseTimeToEpochSeconds(startDateStr) ?: 0L`: If Strava returns an activity with an unparseable or malformed `start_date`, `actEpoch` evaluates to `0L`. Line 781 computes `diff = if (actEpoch > 0) Math.abs(actEpoch - startEpochSeconds) else 0L`. Consequently, any activity with an invalid date gets `diff = 0L`, preferentially beating all real activities!
   - Bug 2: Zero sport-type verification. If a user ran a 5 km run at 10:00 and recorded a 50 km bike ride at 10:04, the duplicate detector considers them the same activity.
   - Bug 3: Zero duration or distance tolerance check. A 2-minute false-start activity recorded 3 minutes before an actual 2-hour workout is matched as a duplicate, suppressing upload of the 2-hour workout and corrupting the false-start activity's metadata.

4. **Potential NullPointerException / Unsafe Response Body Access**:
   - Lines 608, 652, 679: Accessing `response.body!!.string()` without checking if the body is null or empty can trigger an unhandled `NullPointerException`. Safe navigation with `response.body?.string()?.takeIf { it.isNotBlank() }` is required.

5. **`StravaUploadDbHelper.java` Concurrency & SQL Injection Hardening**:
   - `getStravaActivityDataForWorkouts`: SQL query builds `IN ('" + name + "')` string concatenation without SQL bind parameters. While workout filenames are generated by the app, using raw concatenation violates ASPICE / OWASP secure coding standards.
   - `updateOrInsert`: Performs `update(...)` and if updates $< 1$, executes `insert(...)`. This is non-transactional and race-condition prone if concurrent background tasks invoke it. Adding a `UNIQUE` constraint or unique index on `FileBaseName` and utilizing `insertWithOnConflict(..., CONFLICT_REPLACE)` ensures transactional atomicity.

## 2. Root Cause Analysis (Forensic Investigation)

### 2.1 HTTP Status Code Classification Matrix
Under the current implementation, `StravaUploader.uploadToStrava` evaluates response codes via a binary branch:
`responseCode != 201 && responseCode != 200` $\rightarrow$ `retry = false`.
The Strava API v3 documentation specifies the following standard status codes:
- **`200 OK` / `201 Created`**: Upload received and created. Polling required.
- **`400 Bad Request`**: Malformed payload, invalid file encoding. Non-retryable (`retry = false`).
- **`401 Unauthorized`**: Expired or invalid token. If token refresh fails, non-retryable (`retry = false`).
- **`403 Forbidden`**: Insufficient permissions / scope. Non-retryable (`retry = false`).
- **`404 Not Found`**: Resource does not exist. Non-retryable (`retry = false`).
- **`409 Conflict` / duplicate activity**: Handled by duplicate checking logic.
- **`422 Unprocessable Entity`**: Corrupted file or unsupported format. Non-retryable (`retry = false`).
- **`429 Too Many Requests`**: Athlete or application rate limit exceeded (15-min or daily window). **Transient & Retryable (`retry = true`)**. Should log `X-RateLimit-Usage` / `X-RateLimit-Limit`.
- **`500 Internal Server Error`, `502 Bad Gateway`, `503 Service Unavailable`, `504 Gateway Timeout`**: Server-side transient outages or gateway drops. **Transient & Retryable (`retry = true`)**.

### 2.2 Polling Loop Short-Circuit
The polling loop:
```kotlin
for (attempt in 1..MAX_REQUESTS) {
    if (exportResult != null) break
    ...
    val uploadStatusJsonAnswer = getStravaUploadStatus(uploadId)
    if (uploadStatusJsonAnswer == null) {
        exportResult = ExportResult(false, false, "no correct response from Strava")
        continue
    }
    ...
}
```
If `attempt = 1` encounters an intermittent connection reset or packet drop, `uploadStatusJsonAnswer` is null. The loop sets `exportResult` and `continue`s to the top of the loop. At the next iteration, `if (exportResult != null) break` trips immediately, terminating the loop after 1 attempt!
**Correction**: An intermittent null response during polling should log a warning and continue polling up to `MAX_REQUESTS`. Only if all attempts exhaust without reaching a terminal status (`ready`, `error`, `deleted`) should it fail, returning `ExportResult(false, true, "Timeout waiting for Strava processing")`.

### 2.3 Pre-Upload Duplicate False Positive Mechanisms
In `findExistingStravaActivity(startEpochSeconds)`:
1. `parseTimeToEpochSeconds(startDateStr) ?: 0L`:
   When `actEpoch == 0L`, `diff` is set to `0L`. This causes any unparseable date to be evaluated as an exact 0-second difference, taking precedence over valid matching workouts.
   **Correction**: Unparseable dates (`actEpoch <= 0L`) must be skipped (`continue`).
2. Absence of sport type matching:
   Strava athlete activities return `type` and `sport_type` (e.g. `Ride`, `Run`, `Hike`).
   `findExistingStravaActivityForWorkout` has access to `fileBaseName`, which maps to `WorkoutSummaries.SPORT_ID` and `BSportType` (BIKE, RUN, etc.).
   Matching against an existing Strava activity must ensure that either the sport types are compatible (e.g. `BSportType.BIKE` matches `Ride`, `MountainBikeRide`, `GravelRide`, `VirtualRide`, `EBikeRide`; `BSportType.RUN` matches `Run`, `TrailRun`, `VirtualRun`) or Strava activity type is unknown.
3. Absence of duration tolerance:
   `WorkoutSummaries` contains `TIME_TOTAL` (workout duration in seconds).
   Strava activities contain `elapsed_time` (or `moving_time`).
   If a workout was 1 hour (3600 s) and the Strava activity within 5 minutes was a 120-second false start, the ratio $|T_{\text{strava}} - T_{\text{local}}| / \max(T_{\text{strava}}, T_{\text{local}})$ is $> 95\%$. Matching should require duration compatibility (e.g. within $\pm 25\%$ or within 15 minutes, or skipped if duration is unknown/zero).

### 2.4 SQL Security & Concurrency
- `StravaUploadDbHelper.java:291`:
  ```java
  inClause.append("'").append(name).append("'");
  ```
  Must be replaced with `?` placeholders and parameterized arguments:
  ```java
  String[] placeholders = new String[fileNames.size()];
  Arrays.fill(placeholders, "?");
  String selection = WorkoutSummaries.FILE_BASE_NAME + " IN (" + TextUtils.join(",", placeholders) + ")";
  String[] selectionArgs = fileNames.toArray(new String[0]);
  ```
- `updateOrInsert`:
  Add unique index or constraint on `FileBaseName` and wrap in transaction, or use `insertWithOnConflict(TABLE, null, values, SQLiteDatabase.CONFLICT_REPLACE)`.

## 3. User Scope Grounding (ATT-1250)

* **In-Scope Goals**:
  1. Classify HTTP status codes accurately in `StravaUploader.uploadToStrava`:
     - 429 and 5xx return `ExportResult(false, true, ...)` (retryable).
     - 4xx (400, 403, 404, 422) return `ExportResult(false, false, ...)` (non-retryable).
     - Log rate limit headers (`X-RateLimit-*`) on 429.
  2. Make polling status resilient: do not abort the polling loop on a single transient null response; continue polling until `MAX_REQUESTS`. If timeout occurs, return `retry = true`.
  3. Harden pre-upload duplicate discovery:
     - Discard Strava activities with unparseable or invalid start dates (`actEpoch <= 0L`).
     - Compare sport type compatibility with local workout.
     - Compare workout duration tolerance ($\pm 25\%$ or $\pm 15$ min) to avoid attaching to short false-starts.
  4. Fix safe body string reads: replace `response.body!!.string()` with null-safe reads.
  5. Harden `StravaUploadDbHelper.java`: parameterized SQL queries for `getStravaActivityDataForWorkouts` and atomic `insertWithOnConflict` with `CONFLICT_REPLACE`.
* **Out-of-Scope Non-Goals (Scope Bounding)**:
  - Do NOT modify the core OAuth token refresh workflow (`StravaHelper.getRefreshedAccessToken()`).
  - Do NOT rewrite or replace `StravaActivityParser` or `StravaActivitySection` UI.
  - Do NOT change the duplicate naming resolution rules established in `REQ-EXP-008` (preserving custom Strava titles vs app names).

## 4. Requirement Archaeology & Chesterton's Fence Audit

* **Original Requirement ID & Target**: `REQ-EXP-008` (*Smart Asymmetric Workout Naming Strategy & Pre-Upload Duplicate Discovery for Strava*) and net-new `REQ-EXP-021` (*Strava Upload Transient Error Resilient Retry & Duplicate Matching Guard*).
* **Historical Origin & Commit Trace**:
  - `REQ-EXP-008` was introduced in `ATT-902` / `ATT-1105` to prevent creating duplicate activities on Strava when re-uploading an existing workout.
  - The $\pm 300\text{ s}$ window was chosen to accommodate GPS clock drift or minor timezone differences.
* **Root Reason for Existing Formulation**:
  - The original duplicate search used only `startEpochSeconds` because the primary goal was catching exact re-uploads of the same workout where the start time was identical.
  - Sport type and duration checks were omitted for simplicity during initial implementation, inadvertently allowing false-start workouts or cross-sport activities recorded within 5 minutes to trigger false duplicate matches.
* **Preservation of Core Invariants**:
  - Preserving `REQ-EXP-008` behavior: When a genuine matching activity is found on Strava, TCX upload is bypassed, Strava's cloud title is preserved, and metadata enrichment proceeds.
  - By adding sport compatibility and duration checks, false matches are eliminated, ensuring true duplicates still match while false-starts are rejected.
  - All 3,361 tests across the suite remain 100% passing.
