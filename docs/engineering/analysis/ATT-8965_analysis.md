# Stage 1 Analysis: ATT-8965 — Extended Sensor Search & Reconnect Backoff + Search Settings

**Ticket**: `ATT-8965` (`2 SP`, Epic `ATT-5910`) | **Target**: Sprint `2026-11-19_01_Früh`  
**Owner**: Agent 1 (Implementer) | **Branch**: `feature/ATT-8965`

## 1. Problem Statement & Motivation
PO testing of `ATT-7924` on Pixel 10 (`com.atrainingtracker.debug`) with a Polar Verity Sense exposed two search/reconnect flaws:
1. During active workouts (`TrackingMode.TRACKING` / `PAUSED`), `MyBTLEDevice` caps exponential reconnect backoff at `MAX_RECONNECT_DELAY_MS = 16000L` (`1s -> 2s -> 4s -> 8s -> 16s` indefinitely), draining phone BLE radio/battery when a sensor stays out of range for minutes (e.g., swimming).
2. In `PolarOnlineStreamingBridge` (Live-IMU mode) and pre-workout / Start-tab searches, once `DeviceManager.mMyRemoteDeviceTries` (`default = 3`) is exhausted, `DeviceManager.mSearchingStoppedForOneReceiver` shuts down and removes the device permanently unless manually restarted, with no user toggle or configurable steady-state re-search period in Search Settings.

## 2. Root Cause Analysis & Independent Hypothesis Verification
1. **Hard 16 s BLE Ceiling (`MyBTLEDevice.java`)**: Lines `493` (`mSearchTimeoutRunnable`) and `604` (`mGattCallback.onConnectionStateChange`) compute `Math.min(mCurrentReconnectDelayMs * 2, MAX_RECONNECT_DELAY_MS)` using `MAX_RECONNECT_DELAY_MS = 16000L` (`L73`). However, `SystemLiveTrackingRequirementsContractTest.kt:163-168` reflects on `MyBTLEDevice.MAX_RECONNECT_DELAY_MS` and asserts `== 16000L` (`SYSREQ-TRK-002`). Thus `MAX_RECONNECT_DELAY_MS` MUST stay `16000L` as a constant while extended progression (`32s -> 64s -> 128s -> finalPeriodMs`, default `5 min`) is computed via a dedicated Kotlin backoff policy.
2. **Permanent Removal After Try Exhaustion (`DeviceManager.java`, `1,707` LoC)**: In `mSearchingStoppedForOneReceiver` (`L155-169`), `!success && tries <= 1 && !current.shouldKeepAliveOnSearchTimeout()` calls `current.shutDown()` and removes `deviceID` from `mMyRemoteDevices`. `ArchitectureConformanceContractTest.kt:129` caps `DeviceManager.java <= 1,708` LoC (`REQ-CON-051.3`), requiring periodic re-search scheduling to live in a new Kotlin coordinator so `DeviceManager.java` does not grow above cap.
3. **Missing Long-Term Retry in Polar Live-IMU Bridge (`PolarOnlineStreamingBridge.kt`, `1,089` LoC)**: Inherits `MyRemoteDevice.shouldKeepAliveOnSearchTimeout() = false`; `onSearchTimeout()` (`L261-273`) disconnects `polarApi` and emits `notifyStopSearching(false)`, and `deviceDisconnected()` (`L350-369`) tears down active streams without scheduling extended backoff re-attempts after initial search exhaustion.
4. **Dual Search Settings UI & Monolith Guard (`TrainingApplication.java`, `2,135` LoC)**: Search preferences live in `PreferenceManager.getDefaultSharedPreferences` + `xml/prefs_search.xml` and are rendered in BOTH `SearchSettingsDialog.kt` (Settings drawer sheet) and `SensorSearchTuningSection.kt` (Expert Tuning accordion, bound by `docs/design_guidelines.md` §1.4 `TuningToggleItem` / `TuningSegmentedButtonRow`). Because `TrainingApplication.java` is at its exact `2,135` LoC ceiling (`ArchitectureConformanceContractTest.kt:123`), new preference helpers MUST live in a dedicated Kotlin helper instead of growing `TrainingApplication.java`.

## 3. Scope Grounding & Non-Goals
