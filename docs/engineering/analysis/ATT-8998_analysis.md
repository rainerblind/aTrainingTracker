# Stage 1 Analysis: ATT-8998 - MyBTLEDevice & DeviceManager BLE Search-Queue Deadlock

**Ticket**: [ATT-8998](https://rainerblind.atlassian.net/browse/ATT-8998) | **Parent Epic**: [ATT-5910](https://rainerblind.atlassian.net/browse/ATT-5910) | **Severity**: Critical | **SP**: 2  
**Branch**: `feature/ATT-8998` (off `sprint/2026-11-18_03_Nacht` @ `941a1ea5`) | **Author**: AI Agent 1 | **Date**: 2026-11-18

## 1. Problem Statement & Motivation
When resuming a workout (*"Ich möchte dieses Training fortsetzen"*) or searching mid-workout (`TrackingMode.TRACKING` / `PAUSED`), `DeviceManager.startSearchForPairedDevices()` queues all paired sensors sequentially. If an offline BLE peripheral (e.g. BLE Radar) is polled before remaining sensors (e.g. second HRM), its 5s search timeout fails to terminate queue search, leaving `BANALService.isSearching() == true` indefinitely and never searching subsequent queued sensors.

## 2. Root Cause Analysis & Independent Hypothesis Verification
- **Deadlock Path**: `DeviceManager.searchForNextRemoteDevice()` (`DeviceManager.java:941-981`) sets `cMyRemoteDeviceCurrentlySearchingFor = next` (`:947`) and invokes `next.startSearching()` (`:971`), which sets `MyRemoteDevice.mSearching = true` (`MyRemoteDevice.java:79`), `MyBTLEDevice.mState = State.SEARCHING` (`MyBTLEDevice.java:778`), and schedules `mSearchTimeoutRunnable` (`:786`).
- **Missing Stop Broadcast**: When `mSearchTimeoutRunnable` fires (`MyBTLEDevice.java:469-505`), `isMidSessionOrWorkoutActive()` (`:932-934`) returns `true` for ANY sensor whenever `TrackingMode` is `TRACKING`/`PAUSED` (even if `mHasConnectedInSession == false`). The branch (`:479-499`) schedules `mReconnectRunnable` (`:488`) and `triggerGattConnect(dev, true)` (`:496`) but never resets `mState` from `SEARCHING` and never calls `notifyStopSearching(false)` (only called in the `else` branch at `:501`).
- **Queue Stall**: Because `SEARCHING_STOPPED_FOR_ONE_INTENT` is never broadcast, `DeviceManager.mSearchingStoppedForOneReceiver` (`DeviceManager.java:141-177`) never clears `cMyRemoteDeviceCurrentlySearchingFor` or calls `searchForNextRemoteDevice()`. `BANALService.isSearching()` (`BANALService.java:303-308` -> `DeviceManager.isSearchingForARemoteDevice()` `:745-747`) stays `true` forever, blocking `TrainingApplication.addActionsToNotificationBuilder()` (`:1749`), `TrackerService.onSearchingFinished()` (`:979, 1370`), and re-search (`DeviceManager.java:1000-1004`).
- **Independent Peer Review & Verification**: Live inspection confirms the ticket hypothesis and exposes 3 critical coupling constraints:
  1. Calling `notifyStopSearching(false)` alone triggers `DeviceManager.mSearchingStoppedForOneReceiver` (`:157-162`): if `tries == null || tries <= 1`, it calls `current.shutDown()` + `mMyRemoteDevices.remove(deviceID)`, destroying `mReconnectRunnable` and `mBluetoothGatt` (`autoConnect=true`).
  2. `mReconnectRunnable` (`MyBTLEDevice.java:519-521`) calls `startSearching()` (`:769`), which sets `mSearching = true` and `mState = SEARCHING`. If a subsequent `startSearchForPairedDevices()` hits that device, `DeviceManager.searchForNextRemoteDevice()` (`:954-957`) logs `BUG` and executes `break;` with `cMyRemoteDeviceCurrentlySearchingFor` still non-null, deadlocking the queue again.
  3. `triggerGattConnect()` (`MyBTLEDevice.java:286`) and `onScanResult()` (`:360`) require `mState == State.SEARCHING`; resetting `mState = DISCONNECTED` before `triggerGattConnect(dev, true)` at `:496` would silently skip `autoConnect=true`.
  4. Siblings `MyANTDevice` (`MyANTDevice.java:141-161`) and `PolarOnlineStreamingBridge` (`PolarOnlineStreamingBridge.kt:261-273, 488-496`) always call `notifyStopSearching(false)` on timeout/failure; defect is isolated to `MyBTLEDevice` + `DeviceManager`.

## 3. User Scope Grounding & Non-Goals (ATT-1250)
- **In-Scope**: (1) Unblock `DeviceManager` sequential search queue on `MyBTLEDevice` timeout (`notifyStopSearching(false)` + state cleanup); (2) Decouple background mid-session/active-workout reconnect from `DeviceManager` queue ownership and `tries <= 1` teardown; (3) Unit tests in `DeviceManagerSearchQueueTest.kt` / `BLEReconnectRobustnessTest.kt`; (4) Update `DOC-ARC-DD-BTLE` / `DOC-ARC-DD-BANAL`.
- **Non-Goals (Out-of-Scope)**: No ANT+ (`MyANTDevice`) changes, no `PolarOnlineStreamingBridge` changes, no UI/settings changes, no `DeviceManager` monolith extraction beyond LoC ceiling compliance (2 SP confirmed).

## 4. Requirement Archaeology & Chesterton's Fence Audit (REQ-PRO-022)
- **Original Requirement ID & Target**: `REQ-CON-020.2/.3` & `REQ-CON-036.1/.2` (`MyBTLEDevice.java`, `DeviceManager.java`).
- **Historical Origin & Commit Trace**: `ATT-4007` (`e84383ee`), `ATT-5489` (`22d8c54d`), `ATT-7755` (`3dc19303` introducing `isMidSessionOrWorkoutActive()`).
- **Root Reason for Existing Formulation**: `ATT-7755` skipped `disconnectFromGatt()`/`notifyStopSearching(false)` in `mSearchTimeoutRunnable` so mid-workout disconnects would persist `mReconnectRunnable` + `autoConnect=true` instead of being abandoned. It assumed `cMyRemoteDeviceCurrentlySearchingFor == null` during mid-workout disconnects, overlooking active `mSearchQueue` scans on workout resume or mid-workout re-search.
- **Preservation of Core Invariants**: Initial startup search (`TrackingMode.READY`, `!mHasConnectedInSession`) MUST still terminate cleanly after bounded tries (`REQ-CON-036.1`); mid-session disconnects (`mHasConnectedInSession == true`) MUST continue exponential-backoff + `autoConnect=true` recovery without premature `shutDown()`.

## 6. Architectural Strategy & Downstream Regression Guardrails
- Always release the active queue slot (`notifyStopSearching(false)` + transition `mState` out of `SEARCHING`) when `mSearchTimeoutRunnable` expires, while scheduling background reconnect (`autoConnect=true` + `mReconnectRunnable`) only when eligible without hijacking `cMyRemoteDeviceCurrentlySearchingFor` or leaving `MyRemoteDevice.mSearching == true` across queue boundaries.
- Guard `DeviceManager.mSearchingStoppedForOneReceiver` (`tries <= 1`) against shutting down devices actively persisting mid-session background reconnect, keeping `DeviceManager.java <= 1,708` LoC.
- **Downstream Regression Guardrails**: Verify `triggerGattConnect(dev, true)` still executes when `mBluetoothGatt == null`; verify `searchForNextRemoteDevice()` never stalls on `next.isSearching()`; verify `shutDown()` cancels `mReconnectRunnable` and closes GATT; verify `BANALService.isSearching()` returns `false` once queue drains.
