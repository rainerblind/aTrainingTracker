## 1. Problem Statement & Forensic Root Cause Analysis
* **Current Defects on Live `sprint/2026-11-22_01_Früh`**:
  1. `SettingsDataStore` (`SettingsDataStore.kt:121-124, 762`) exposes a `public` constructor retaining raw `context: Context` and creating an uncancelled `CoroutineScope(SupervisorJob() + Dispatchers.Default)` per instance (`snapshotStateFlow` eager `stateIn` at `:854`, `launchSetAthleteWeightKg` at `:890`). Five production sites construct `SettingsDataStore(...)` directly instead of `getInstance(...)`.
  2. `ProFeatureManager` (`ProFeatureManager.kt:42-48, 81-116`) exposes a `public` `@JvmOverloads` constructor retaining raw `context: Context`, creating a fresh `SupervisorJob` scope, launching `checkAndPersistPioneerEligibility()`, and starting 3 `SharingStarted.Eagerly` `stateIn` collectors per instance. Two production UI sites bypass `getInstance(context)`.
  3. `MyPreferenceManager` (`MyPreferenceManager.kt:149-151`) has a `public` non-singleton constructor allocating an unclosed `CoroutineScope(SupervisorJob() + Dispatchers.IO)` on every call across 17 production sites (including 6 ephemeral one-shot calls in drawer/back-handler filter clearing).
  4. `ATrainingTrackerMap.kt:215-216` still mounts a dead collector `val tuningConfig by tuningDataStore.tuningConfigFlow.collectAsState(initial = TuningConfig())` whose value is never read anywhere in the file.

## 2. Independent Peer Review & Verification (4-Augen-Prinzip)
* **Already Resolved Upstream (Delta vs. Ticket Baseline `2026-46.7`)**: `TuningPreferencesDataStore` (`:554-560, 1007-1030`) was already converted to `private constructor`, `applicationContext` normalization, `createForTesting`, and zero external production/test direct constructor callers in `ATT-7874` (`6dffe9e7`, `REQ-TRK-079.1`) and refined in `ATT-6048` (`a88a0672`, `REQ-SET-121`). Its regression guard `TuningPreferencesDataStoreLifecycleTest.kt` already passes.
* **Additional Unlisted Leak Site Found**: `SupporterDebugSection.kt:252` directly calls `ProFeatureManager(context)` (in addition to `ATrainingTrackerApp.kt:890` cited in the ticket).
* **Critical Cross-Test Singleton Isolation Risk (`Rule 66` / §5.5)**: Plain-JVM MockK ViewModel tests (e.g. `TrackingViewModelHrvTest`, `EditWorkoutViewModelTest`) pass unmocked `Application` where `resolveDataStore`/`resolveUserPreferencesDataStore` falls back to `InMemoryPreferencesDataStore()`. Caching that fallback inside `INSTANCE` without guarding against subsequent Robolectric tests (`HrvDfaA1RangeSliderGestureTest`, `ViewModelRepositoryIntegrationTest`, `EditWorkoutPolarRetrySyncUiTest`) in the same JVM fork would poison real-`filesDir` tests. `getInstance` must upgrade an auto-created `InMemoryPreferencesDataStore` fallback when a real `filesDir` context arrives (while preserving explicit `setInstanceForTesting` overrides and identical singleton references across consecutive MockK contexts).

* **Out-of-Scope**: `TuningPreferencesDataStore` (already private & compliant per `ATT-7874`/`ATT-6048`); `BoundedPref`/Auto-Pause (`ATT-6048`); UI/strings changes (`0` strings).
* **Chesterton's Fence Audit**: Extends `REQ-TRK-079.1` (`ATT-7874`, `6dffe9e7`) & `REQ-SET-079` (`DataStoreHotPathContractTest`) via net-new `REQ-SET-128`; preserves zero `runBlocking` in `SettingsDataStore` reads, `TuningPreferencesDataStore.kt <= 2,410` LoC, `InMemoryPreferencesDataStore` JVM test fallback, and `ProFeatureManager` constructor-injection test seam via `createForTesting`.
