## 1. Problem Statement & Motivation
* Pixel 10 field run (`2026-11-19_184953`, `Kurze Runde var 2 #53`, `Sport = RUN`, 44 min carried continuously in a front-hip Salomon running belt with one slow stretch at `19:12:54–19:18:04` climbing over fallen trees) produced severely miscalibrated `ACTIVITY_AND_CARRIAGE_MODE` telemetry:
  * `RUN_WAIST_HIP (5)`: **`8 s` (`0.3%`)** vs. ~85–90% ground truth.
  * `WALKING_TRANSITION (1)`: **`1,386 s` (`52.2%`)** (easy-pace running trapped in walking).
  * `RUN_HANDHELD (7)`: **`911 s` (`34.3%`)** (front-hip belt pelvic twist/bounce kicked out of waist/hip).
  * `BIKE_FRONT_POCKET (4)` (`343 s`, `12.9%`) + `BIKE_JERSEY_BACK (3)` (`3 s`, `0.1%`): cycling modes fired during an explicit `RUN` workout.
  * **389 mode switches** across 44 minutes (`6.8 s` mean segment duration), degrading `SmartphoneImuCadenceEstimator` and inflating `rBaroM2` (`0.5 -> 1.5–2.0`) in `AltitudeAndSlopeDevice_ATTFused`.
* **Expected**: `0%` cycling modes during `Sport = RUN` without wheel speed or `>= 5.5 m/s`; easy-pace running (`~1.8–2.5 m/s`) in a front-hip belt predominantly classifies as `RUN_WAIST_HIP (5)` while genuine slow obstacle/walking stretches (`< 1.3–1.5 m/s` or low vertical impact) still enter `WALKING_TRANSITION (1)`; and steady running exhibits drastically reduced chatter without regressing `ATT-9062` (`REQ-FIL-034`) or cycling/dismount/wrist-glance tests.

## 2. Root Cause Analysis & Independent Hypothesis Verification
* **Verified Root Causes on `sprint/2026-11-19_03_Nacht` (`e11a8123`, post-`ATT-9062`)**:
  1. **Soft Sport-Context Prior Allows Cycling Bleed (`PhoneCarriageClassifier.kt:514-568`)**: `sportHint == SportContextHint.RUNNING` only adds `runningPrior += 2.5` while all 3 `BIKE_*` modes still compete. When `scoreRunWaistHip` drops negative on a front-hip belt (`-0.9`), `scoreBikeFrontPocket` (`+7.8`) overcomes `+2.5` (and even `+5.0`), letting `BIKE_FRONT_POCKET` win with `wheelSpeed == null` and `effectiveSpeed < 5.5 m/s`.
  2. **Easy-Pace Running Trapped in `WALKING_TRANSITION` (`PhoneCarriageClassifier.kt:487-509`)**: `walkingStepBand` (`1.15..2.30 Hz` up to `2.50 m/s`) short-circuits easy trail-jogging cadences (`2.15–2.29 Hz` or dropped step events), while `isStepHarmonicWalking` (`effectiveSpeed <= 2.15 || sportHint != RUNNING`) and `isPendulumWalking` (unbounded by `sportHint` up to `2.50 m/s`) short-circuit easy runs (`1.8–2.5 m/s`) whenever `TYPE_STEP_DETECTOR` batches/drops steps—without consulting `accelEval` vertical impact RMS.
  3. **Hard Penalty Cliffs in `scoreRunWaistHip()` (`PhoneCarriageClassifier.kt:659-738`)**: Rigid rear-clip thresholds inflict a `-4.6` cliff at `swingSdDeg >= 10.0°` (`+2.6 -> -2.0`) and a `-3.7` cliff at `yawResidualRms > 0.38` (`+2.2 -> -1.5`). Elastic front-hip belts routinely exhibit `swingSdDeg = 10–15°` and `yawResidualRms = 0.38–0.65 rad/s` with `glanceCount == 0`, causing `scoreRunWaistHip` (`-0.9`) to lose badly to `scoreRunHandheld` (`+6.4`) and `scoreRunBicepArm` (`+3.7`).
  4. **Razor-Thin Score Margin & Fast `RUN -> WALK` Dwell (`PhoneCarriageClassifier.kt:103, 403-417, 579-581`)**: `SCORE_MARGIN = 0.25` (~3% of score range) flips `bestMode` on 1-s noise, and `isDismountOrRemountTransition()` applies short `dismountHysteresisMs (2.0 s)` even to `RUN_* -> WALKING_TRANSITION` (letting brief 2-s canopy GPS dips ping-pong `RUN <-> WALK` continuously).
* **Independent Peer Review & Verification (4-Augen-Prinzip Blind Spots, Call-Site & LoC Audit)**:
  * **Blind Spot 1 (Triathlon/Brick Override Preservation — `ATT-8917`)**: Masking `BIKE_*` unconditionally for `sportHint == RUNNING` would block `RUN -> BIKE` brick detection. Masking strictly when `sportHint == RUNNING && !wheelActiveMoving && (wheelSpeed == null || wheelSpeed <= 0.5) && (effectiveSpeed == null || effectiveSpeed < 5.5)` guarantees `0%` cycling during normal running while immediately allowing `BIKE_*` when a wheel sensor activates or cycling speed hits `>= 5.5 m/s`.
  * **Blind Spot 2 (Walking/Dismount Test Parity — `PhoneCarriageClassifierTest:208, 253, 295`, `SpeedAndLocationDevice_ATTFusedTest:2259, 2313`)**: Raising easy-run walking guards globally would break `1.2–2.3 m/s` cycling-dismount walking tests (`sportHint = CYCLING / UNKNOWN`). Scoping easy-run walk suppression strictly to `sportHint == RUNNING && effectiveSpeed >= 1.65` with running-grade vertical impact (`impactRms >= 1.8 m/s²`), easy-run step cadence (`>= 2.15 Hz`), or `effectiveSpeed >= 1.75` without low-impact accel (`impactRms < 1.2 m/s²`) preserves 100% of existing walking/dismount tests AND genuine `< 1.55 m/s` / low-impact obstacle climbs (`19:12–19:18`)!
  * **Blind Spot 3 (`RUN_BICEP_ARM` & `RUN_HANDHELD` Separation — `PhoneCarriageClassifierTest:157-180`, `SpeedAndLocationDevice_ATTFusedTest:813-865`)**: Calibrating `scoreRunWaistHip` for moderate front-hip tiers (`swingSd 10..15.5° -> +1.8`, `yaw 0.48..0.68 -> +1.4`, `baro < 0.45 -> +1.2`, `glance == 0 -> +1.2`), requiring stronger handheld evidence (`swingSd >= 13°`, `yaw >= 0.55`, `glance == 0 -> -0.8`, `glance >= 1 -> +2.8`), and separating bicep pendulum (`swingSd >= 14° -> +2.6`) yields clear positive margins for ALL four: rear clip (`+5.8`), front-hip belt (`+3.7` vs Bicep, `+4.1` vs Handheld), bicep armband (`+4.5`), and handheld with glance (`+6.8`; also keeps `SpeedAndLocationDevice_ATTFusedTest:865` at `RUN_HANDHELD` with `3.1 vs 1.5`).
  * **Blind Spot 4 (Zero Edits Needed to `SpeedAndLocationDevice_ATTFused.kt`)**: `SpeedAndLocationDevice_ATTFused.kt` (`1,459 / 1,500` LoC) already feeds `sportHint`, `wheelSpeed`, `accel`, `rotVec`, `gyro`, `baro`, `step`, and accuracy-gated `gnssSpeed` into `PhoneCarriageClassifier`. Solving `ATT-9157` strictly inside `PhoneCarriageClassifier.kt` (`1,062 -> ~1,135 / 1,500` LoC, `~365` headroom) keeps **`SpeedAndLocationDevice_ATTFused.kt` untouched (`0` LoC delta)** and all protected monoliths at **`0` LoC touched**!
  * **Call-Site Audit**: Sole production caller is `SpeedAndLocationDevice_ATTFused.kt` (`:109`). Downstream consumers (`AltitudeAndSlopeDevice_ATTFused.kt`, `SmartphoneImuCadenceEstimator.kt`, `MultisportTransitionDetector.kt`) consume `PhoneCarriageMode` codes (`-1..7`) and benefit automatically with `0` edits required.
