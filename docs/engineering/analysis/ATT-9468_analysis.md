## 1. Independent Peer Review & Forensic Codebase Verification

Auditing the Jira hypothesis against `sprint/2026-11-24_01_Früh` (`66309b1e`) confirms the primary race condition behind Pixel 10 workout `2026-11-21_081228` (`workoutID = 2423`, `row 425`, `TIME_TOTAL = 1353 s`, `LAP_NR = 4` stranded inside `Lap 6`) and uncovers **four additional blind spots** in live production code:

| Symbol / Location | Verified Baseline (`66309b1e`) | Forensic Finding |
|---|---|---|
| `TrackerService.sampleAndWriteToDb()` (`TrackerService.java:2692-2830`) & `MultisportLapCoordinator.onMultisportTransitionIntent()` (`MultisportLapCoordinator.kt:315-381`) | `mScheduler` snapshots `banalService.getAllSensorData()` (`TIME_TOTAL = 1353`, `LAP_NR = 4`, `summaryValues.LAPS = 4`) on `mScheduler` **before** enqueuing `recordLiveSample` via `mTableInitializationFuture.thenAcceptAsync(..., mDbExecutor)` (`:2793`). Concurrently on Main Looper, `onMultisportTransitionIntent()` calls `planAndCommitAnchorTransition()`, `advanceLapsFn(2, ...)`, and enqueues `persistTask` (`saveLap` + `backfillWorkoutSamplesLapNumbers()`) onto `mDbExecutor` (`:373`). | **Confirmed Primary Root Cause**: Even though `mDbExecutor` is a single-threaded FIFO executor, `persistTask` can enqueue on `mDbExecutor` **before** the already-snapshotted `mScheduler` tick reaches `:2793`. `persistTask` updates `rows 409..424` (`1337..1352 s`) to `LAP_NR = 6`; then the delayed `mScheduler` lambda inserts `row 425` (`1353 s`, `LAP_NR = 4`) and writes stale `WorkoutSummaries.LAPS = 4` (`:2750`) permanently after backfill completes. |
| `BANALService.advanceLapsForMultisport()` (`BANALService.java:525-530`) & `MultisportLapCoordinator.backfillWorkoutSamplesTable()` (`MultisportLapCoordinator.kt:505-528`) | `for (int i = 0; i < lapAdvanceCount; i++) dm.newLap()` bumps `ClockDevice.mLapSensor` one step at a time (`4 -> 5 -> 6`), while `backfillWorkoutSamplesTable()` filters strictly on `AND (LAP_NR = oldLapNr OR LAP_NR IS NULL)` (`:512`, `:525`). | **Blind Spot #1 (Torn Mid-Loop `LAP_NR`)**: If `mScheduler` reads `getAllSensorData()` between `i = 0` (`LAP_NR = 5`) and `i = 1` (`LAP_NR = 6`), the sample captures torn `LAP_NR = 5` at `TIME_TOTAL >= enterS`. Even if inserted *before* `persistTask`, `LAP_NR = 4` fails to match `5`, stranding `LAP_NR = 5` inside `Lap 6`. Replacing `LAP_NR = oldLapNr` with monotonic `LAP_NR < targetLapNr OR LAP_NR IS NULL` upgrades both stale `4` and torn `5` without ever downgrading a later manual lap (`7`). |
| Scalar `minLapNr` vs. Timestamped Transition Windows | Ticket mentions a scalar `minLapNr` floor as one option. | **Blind Spot #2 (Delayed Transition-Window Samples)**: A scalar floor `minLapNr = 6` would mis-tag a delayed sample with `TIME_TOTAL ∈ [exitS, enterS)` (`1320 s`, belonging to `Transition = 5`) as `6`, creating a `5 -> 6 -> 5` inversion (or under `CompletableFuture` LIFO wakeup when `mTableInitializationFuture` is pending). Evaluating an ordered list of committed `CommittedTransitionWindow(exitTotalS, enterTotalS, exitEpochS, enterEpochS, hasTransition, transitionLapNr, newLegLapNr)` by each sample's `TIME_TOTAL` (falling back to UTC `time`/capture epoch) guarantees exact `[exitS, enterS) -> transitionLapNr` and `>= enterS -> newLegLapNr` monotonicity for every sample regardless of queueing order. |
| `TrackerService.endWorkout()` (`TrackerService.java:2382-2549`) & `onStartCommand(START_NORMAL)` (`:1274`) | `handleActionStop()` cancels future `mTrackerHandle` ticks (`:1496`) without draining an in-flight `sampleAndWriteToDb()` tick; rapid Stop -> Start calls `mMultisportLapCoordinator.resetForSession()` synchronously on Main Thread (`:1274`) while prior `endWorkout()` may still be queued on `mDbExecutor`. | **Blind Spot #3 (Stop/Restart Session Isolation & Finalization Reconciliation)**: Tagging committed windows with `baseFileName` and keeping a bounded (`<= 4` entries) `pendingReconciliationByFileName` map allows `resetForSession()` to reset live state for Session 2 while `endWorkout()` still performs an idempotent, fault-isolated `reconcileWorkoutSamplesOnFinalization(context, baseFileName)` on `mDbExecutor` strictly before `WorkoutPostProcessingCoordinator.enqueue()` / `ExportManager` (`0` DB queries on single-sport workouts). |
| `WorkoutSamplesDatabaseManager.java` & `BANALService.java` | `WorkoutSamplesDatabaseManager.java` is untouched per `REQ-FIL-031.3`; `BANALService.java` / `DeviceManager.java` require zero edits. | **Blind Spot #4 (Leaf-Lock Guarantee)**: Making `MultisportLapCoordinator`'s monitor a pure in-memory leaf lock (never calling `BANALService` or SQLite while synchronized) ensures **zero nested locks** and **zero AB-BA deadlock risk** across `mScheduler`, Main Looper, `BANALService`, and `mDbExecutor`. |

## 2. Chesterton's Fence Archaeology (`REQ-PRO-022`)

- **Original Requirement ID & Target**: Net-new `REQ-TRK-096` extending `REQ-FIL-031.3` (`ATT-8917`, `MultisportLapCoordinator` retroactive `WorkoutSamples.db` `LAP_NR` backfill) and `REQ-TRK-030` / `REQ-TRK-034` (`TrackerService` `mDbExecutor` serialization & finalization) across `MultisportLapCoordinator.kt` and `TrackerService.java`.
- **Historical Origin & Commit Trace**: `a93f3230` (`ATT-8917`) introduced `MultisportLapCoordinator` with synchronous `advanceLapsFn()` on Main Thread + asynchronous `backfillWorkoutSamplesLapNumbers()` on `mDbExecutor` to uphold zero main-thread SQLite and zero edits to `WorkoutSamplesDatabaseManager.java`.
- **Root Reason for Existing Formulation**: `advanceLapsFn()` ran synchronously on Main Thread so live cockpit tiles/accumulators updated immediately while SQLite `Laps.db` / `WorkoutSamples.db` writes stayed off the Main Thread on `mDbExecutor`. `WHERE LAP_NR = oldLapNr OR LAP_NR IS NULL` aimed to protect subsequent manual laps from being overwritten by delayed backfills.
- **Preservation of Core Invariants**: Retains zero main-thread SQLite writes, synchronous `advanceLapsFn()` live cockpit update, manual-lap protection (`LAP_NR > newLegLapNr` never downgraded), `REQ-TRK-002` phantom-lap rejection, in-memory pause/resume multisport state retention (`TrackerServiceResumeTest`), `0` edits to `WorkoutSamplesDatabaseManager.java` / `BANALService.java` / `DeviceManager.java` / `WorkoutRepository.kt`, and `TrackerService.java <= 3,220` LoC (`3,184 -> 3,186`).
