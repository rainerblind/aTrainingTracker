# Ticket Deliverable: ATT-8101 — Persist sensor list sort order (DeviceSortOrder) across app restarts

* **Risk Tier**: `tier-b` | **Target Release**: `V5.0.0` | **Parent Epic**: `ATT-5910`
* **Status**: Verified (`REQ-UI-2806`, `TST-UI-2806`)

---

## 1. Problem, Scope & Change-Request Impact Analysis
* **Problem / Root Cause**:
  * In `app/src/main/java/com/atrainingtracker/banalservice/ui/devices/devicetabs/DevicesTabbedViewModel.kt` (lines 189–199), `_sortOrder` is backed exclusively by `SavedStateHandle[KEY_SORT_ORDER]`, defaulting to `DeviceSortOrder.ALPHABETICAL` whenever `SavedStateHandle` is empty.
  * While `SavedStateHandle` survives configuration changes and Android process-death state restoration, it is discarded on normal app termination and cold restart, causing the user's chosen `DeviceSortOrder` (`ALPHABETICAL`, `FIRST_SEEN`, `LAST_USAGE`, `BATTERY_LEVEL`) in `DevicesTabbedScreen` to reset back to `ALPHABETICAL`.
* **In-Scope / Out-of-Scope**:
  * *In-Scope*:
    * Persist `DeviceSortOrder` durably in `SettingsDataStore` (`KEY_DEVICE_SORT_ORDER = stringPreferencesKey("device_sort_order")`, `deviceSortOrderFlow: Flow<DeviceSortOrder>`, `suspend fun setDeviceSortOrder(order: DeviceSortOrder)`), safely falling back to `DeviceSortOrder.ALPHABETICAL` when unset or when an unknown/corrupt token is stored (`safeEnumValueOfOrNull`).
    * Update `DevicesTabbedViewModel` to hydrate `_sortOrder` asynchronously from `settingsDataStore.deviceSortOrderFlow` on `viewModelScope` when `SavedStateHandle` has no valid explicit selection, write selected sort order to both `SavedStateHandle` and `SettingsDataStore`, and prevent stale DataStore emissions from overwriting an active user selection or `SavedStateHandle` state (no `runBlocking`, no flicker back to `ALPHABETICAL`).
    * Add authentic JVM unit tests exercising the real `DevicesTabbedViewModel` paired with `SettingsDataStore.createForTesting(..., InMemoryPreferencesDataStore())` across ViewModel re-instantiation with fresh `SavedStateHandle()`, plus invalid/corrupt stored token fallback.
  * *Out-of-Scope*:
    * Persisting `RouteSortOrder`, `WorkoutSortOrder`, `SegmentSortOrder`, or `ClusterSortOrder`.
    * Changing `DeviceSortOrder` enum values, comparators, or `isNewlyDiscovered` recency pinning (`REQ-UI-528.2`, `REQ-UI-334`).
    * Modifying `Devices.db` SQLite schema or `values*/strings*.xml` (`Localization Parity: N/A - 0 new or modified UI strings`).

* **Chesterton's Fence / Impact**:
  * Refines `REQ-UI-528.4` (`ATT-7663`, commit on `DevicesTabbedViewModel.kt`).
  * `SavedStateHandle[KEY_SORT_ORDER]` was originally used for Activity/Navigation process-death survival. Removing `SavedStateHandle` would drop synchronous frame-0 state restoration across configuration changes and break existing `SavedStateHandle` precedence tests (`testSortOrder_restoredFromSavedStateHandle`). Therefore, `SavedStateHandle` is preserved for synchronous in-session/config-change reactivity while `SettingsDataStore` provides durable cross-restart persistence, guarded so an explicit `SavedStateHandle` or user `setSortOrder(...)` call is never overwritten by an in-flight DataStore read.
  * `DataStoreHotPathContractTest` prohibits `runBlocking` reads in `SettingsDataStore.kt`; therefore all reads/writes remain strictly suspend/`Flow`-based on `viewModelScope` / DataStore IO.

## 2. Decision & Architecture Impact
* **Design Decision & Rationale**:
  * **`SettingsDataStore` Reuse**: `DevicesTabbedViewModel` already injects `settingsDataStore: SettingsDataStore = SettingsDataStore.getInstance(application)` via `@JvmOverloads constructor`. Storing `KEY_DEVICE_SORT_ORDER` in `SettingsDataStore` avoids adding a new constructor dependency (`MyPreferenceManager`), preserves full constructor binary compatibility (`@JvmOverloads`, `Rule 3.5`), and avoids side-effecting tests that mock `SettingsDataStore` via `SettingsDataStore.setInstanceForTesting(...)`.
  * **Flicker-Free Reactivity & Precedence**: `DevicesTabbedViewModel` checks `SavedStateHandle[KEY_SORT_ORDER]` synchronously during initialization (`hasExplicitSortOrderSelection`). Only when `SavedStateHandle` lacks a valid `DeviceSortOrder` does `init` hydrate from `settingsDataStore.deviceSortOrderFlow` on `viewModelScope`, writing the resolved persisted order into both `_sortOrder` and `savedStateHandle`. Calling `setSortOrder(order)` synchronously sets `hasExplicitSortOrderSelection = true`, updates `_sortOrder` and `savedStateHandle`, and asynchronously persists via `settingsDataStore.setDeviceSortOrder(order)`.
* **SWE.2 Architecture / Files Touched**:
  * Production: `app/src/main/java/com/atrainingtracker/trainingtracker/settings/SettingsDataStore.kt`, `app/src/main/java/com/atrainingtracker/banalservice/ui/devices/devicetabs/DevicesTabbedViewModel.kt`.
  * Tests: `app/src/test/java/com/atrainingtracker/banalservice/ui/devices/devicetabs/DevicesTabbedViewModelTest.kt`.
  * Living Docs: `docs/requirements/req_ui_design_system_part6.md`, `docs/tests/tst_ui_design_system_part3.md` (+ synced master indexes).
  * `docs/architecture.md`: unchanged (no new subsystem, service, DB, or requirement prefix family).
