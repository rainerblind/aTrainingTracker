## 1. SWE.2 Architectural Decomposition & Threading Model

- **Single Authoritative Store + Synchronous Cold-Start Mirror (`TuningPreferencesDataStore.kt`)**:
  - Jetpack DataStore (`KEY_RECORD_SMARTPHONE_RAW_TELEMETRY`) remains the authoritative store (`ADR-005`).
  - Default `SharedPreferences` (already warm in memory from `TrainingApplication.onCreate():1491`) holds a 1-key cold-start mirror (`KEY_RECORD_SMARTPHONE_RAW_TELEMETRY.name`), accessed **strictly** when `isRealDataStore = (dataStoreOverride == null)` inside exception-safe helpers.
  - **Constructor Init-Order Invariant**: Declare `isRealDataStore`, `initialRecordSmartphoneRawTelemetry`, `_tuningConfigStateFlow`, `tuningConfigStateFlow`, `_recordSmartphoneRawTelemetryEnabled`, and `recordSmartphoneRawTelemetryEnabled` **strictly before** `init { appScope.launch { ... } }` so the background collector can never observe an uninitialized `MutableStateFlow`.
  - **Delta-Only Mirror Sync (`syncCachedConfig`)**: Both `editAndSync` (used by `saveTuningConfig`, `updateRecordSmartphoneRawTelemetryEnabled`, `resetToDefaults`) and the `init` DataStore collector call `syncCachedConfig(cfg)` to atomically update `_tuningConfigStateFlow`, `_recordSmartphoneRawTelemetryEnabled`, radar callbacks, and (only when the mirrored boolean differs from `cfg.recordSmartphoneRawTelemetryEnabled`) `sp.edit().putBoolean(...).apply()` -> zero steady-state disk writes on fresh installs or unchanged boots.
- **Java Bridge & Recorder Delegation**:
  - `SettingsDataStoreJavaHelper.isRecordSmartphoneRawTelemetryEnabled(context)` reads `getTuningConfig(context).recordSmartphoneRawTelemetryEnabled` in $O(1)$ (matching `isPostWorkoutErtsSmoothingEnabled` and all other `TuningConfig` helpers; 100% `mockkStatic` and `mockk<TuningPreferencesDataStore>()` compatible).
  - `SmartphoneRawTelemetryRecorder.isEnabled(context)` removes `runBlocking { ...recordSmartphoneRawTelemetryFlow.first() }` and delegates directly to `SettingsDataStoreJavaHelper.isRecordSmartphoneRawTelemetryEnabled(context)` inside its `try/catch` guard.
- **Dispatcher / Threading**: Main thread (`TrackerService`, Compose UI) performs only $O(1)$ volatile/in-memory reads (`StateFlow.value` / already-warm `SharedPreferences` map on first instance init); DataStore I/O stays on DataStore's `Dispatchers.IO` and `appScope` (`Dispatchers.Default`).
- **Continuous SWE.2 / SWE.3 Maintenance**: No new subsystem/repository/FGS and `0` edits to `TrackerService.java`, `BANALService`, or `MyBTLEDevice` -> `docs/architecture.md` and `docs/architecture/detailed_design/tracker_service.md` require no updates.
- **Monolith Ceiling (`ArchitectureConformanceContractTest`)**: `TuningPreferencesDataStore.kt` `2,239 -> ~2,265` LoC (`<= 2,410` cap); `SettingsDataStoreJavaHelper.kt` `~370` LoC (`<= 1,500`); `SmartphoneRawTelemetryRecorder.kt` `~832` LoC (`<= 1,500`).
