## 1. Requirement Specification (`REQ-SET-130`) & Given-When-Then Acceptance Criteria
1. **`REQ-SET-130.1` — Pure-JVM UTC Anchor Alignment & Timezone-Safe Entry Selection (`PolarOfflineHrTimestampAligner`)**:
   - *Normative*: A dedicated pure-JVM helper (`PolarOfflineHrTimestampAligner`, zero `android.*` imports) SHALL resolve `PolarOfflineRecordingData.HrOfflineRecording.startTime` (`LocalDateTime` parsed as UTC by Polar BLE SDK `8.6.0` `OfflineRecordingData.parseStartTime`) strictly via `ZoneOffset.UTC` (`startTime.toInstant(ZoneOffset.UTC).toEpochMilli()`) rather than `ZoneId.systemDefault()`, falling back to `fallbackAnchorMs` ONLY when `startTime` is null, `< 2020`, or yields `<= 0L`. It SHALL align valid 1-Hz samples (`25..250 bpm`, `hr > 0 ? hr : correctedHr`) to `anchorMs + index * 1_000L`, resolve `Types.PbLocalDateTime` via `ZoneOffset.ofTotalSeconds(timeZoneOffset * 60)` strictly when `hasTimeZoneOffset()` is true AND `timeZoneOffset in -1080..1080` (else `fallbackZone`, preventing `DateTimeException` on malformed protobuf bytes), and match `PolarOfflineRecordingEntry` entries within `[windowStartMs - toleranceMs, effectiveEndMs + toleranceMs]` evaluating all valid local offsets (`zoneId.rules.getValidOffsets(entry.date)` for DST fall-back overlap hours) first and falling back to UTC path interpretation ONLY when zero local matches exist in a non-UTC timezone.
   - *Given* a device in `Europe/Berlin` (`CET +1`, `CEST +2`, or DST fall-back overlap hour) or `America/New_York` (`UTC-5`) with UTC `WorkoutSamples.time` (`09:43:06Z..09:45:29Z`) and Polar SDK `HrOfflineRecording.startTime = 2026-11-22T09:43:08`, *When* `resolveHrOfflineAnchorMs()` and `alignHrSamples()` execute, *Then* `anchorMs` resolves to exact `2026-11-22T09:43:08Z` with zero timezone shift and each 1-Hz sample aligns to its exact workout second.
2. **`REQ-SET-130.2` — Bounded Nearest-Sample Matching in `WorkoutSamplesDatabaseManager.patchMissingHeartRateSamples()`**:
   - *Normative*: `WorkoutSamplesDatabaseManager.patchMissingHeartRateSamples()` SHALL enforce a strict maximum timestamp matching tolerance `MAX_HR_MATCH_TOLERANCE_MS = 5_000L` (`<= 5 s`) when selecting the nearer of `hrMap.floorEntry(tsMs)` and `hrMap.ceilingEntry(tsMs)` for every missing `SensorType.HR` row (`HR IS NULL OR HR <= 0`). Any missing row whose nearest offline HR sample exceeds `5_000 ms` MUST be skipped (left `NULL`/unmodified, never flat-line clamped to an out-of-window endpoint). Existing valid HR, GPS, speed, cadence, and power columns, the `totalRows == 0` empty-table insert path, and the exact public JVM signature MUST be preserved.
   - *Given* a workout with missing HR rows at `09:43:06Z..09:45:20Z` and an offline HR series shifted by `1 h` (`08:43:08Z..08:45:29Z`) or missing an unrecorded 13 s leading gap (`tsMs < firstSampleMs - 5_000L`), *When* `patchMissingHeartRateSamples()` executes, *Then* out-of-window rows remain unpatched (`0` patched for 1-hour shifted series; only rows within `<= 5_000 ms` patched for partial overlap) with zero constant-value flat-line corruption.
3. **`REQ-SET-130.3` — Commit-Gated Flash Cleanup, Complete-HR Pending Fast Path & Structured Diagnostics (Verity Sense + H10 Parity)**:
   - *Normative*: `PolarVeritySenseOfflineController.executePendingSyncSession()` SHALL add a symmetric zero-gap fast path when `session.offlineEntry != null && !baseFileName.isNullOrEmpty() && !shouldBackfill(appContext, baseFileName)` (preserving full `session.swimSession` backfill): skip PFTP HR download, log `Log.i` (`alreadyCompleteHr=true`), clear `polarSyncPending`, remove the matched flash entry, refresh the workout, and return `true`. In `applyBackfillAndCommit()` (defense-in-depth), capture `patchedCount` from `PolarOfflineGattCoordinator.patchMissingHeartRateAndRecordSensorType()`; whenever `baseFileName.isNullOrEmpty()`, `hrPairs.isEmpty()`, or `(patchedCount <= 0 && hasMissingHeartRateSamples(baseFileName))`, it MUST skip `recomputeHrSummaryMetrics()`, MUST NOT clear `polarSyncPending`, MUST log `Log.w`, and MUST return `false` so neither `handleStopBackfillMatch()` nor `executePendingSyncSession()` invokes `api.removeOfflineRecord()`. When `patchedCount == 0 && !hasMissingHeartRateSamples(baseFileName)` (non-empty `baseFileName` & `hrPairs`), it SHALL log `Log.i`, clear pending if requested, refresh the workout, and return `true` (no pending-retry livelock). Both `PolarVeritySenseOfflineController` and `PolarH10OfflineController` SHALL emit structured `Log.i` diagnostics (`Log.w` on zero-patch rejection) recording `workoutId`, matched `entry.path`, `startTime` (Verity), `anchorMs`, `samples`/`beats`, `hrRange=[min..max]`, `patchedCount`, and `flashRemoved`.
   - *Given* `patchMissingHeartRateSamples()` returns `0` while `hasMissingHeartRateSamples == true`, *When* `stopAndBackfillWorkout()` or `syncPendingWorkout()` runs, *Then* `applyBackfillAndCommit()` returns `false`, `api.removeOfflineRecord()` and `clearPolarSyncPending()` are called `0` times, and stop-time backfill persists `setPolarSyncPending()`; conversely, when `hasMissingHeartRateSamples == false`, `executePendingSyncSession()` fast-paths cleanup and `applyBackfillAndCommit()` returns `true` cleanly without livelock.
4. **`REQ-SET-130.4` — Monolith Ceilings, Pinned Signatures & Zero UI/DB/String Side Effects**:
   - *Normative*: `PolarVeritySenseOfflineController.kt <= 1,500` LoC (reduced below `1,492` via `PolarOfflineHrTimestampAligner.kt`), `PolarH10OfflineController.kt <= 1,500` LoC, `WorkoutSamplesDatabaseManager.java <= 1,500` LoC with unchanged public JVM signatures (`InterfaceSignatureDriftContractTest`); zero `WorkoutRr.db` / `HrvPostWorkoutRecomputer` writes on Verity Sense (`REQ-SET-109.2`); zero DB schema bumps; `0` edits to `PolarOfflineGattCoordinator.kt`, `PolarOnlineStreamingBridge.kt`, `TrackerService.java`, and `res/values*/strings*.xml` (`Localization Parity: N/A - 0 string changes`).

## 2. Requirement Archaeology & Chesterton's Fence Audit (`REQ-PRO-022`)
1. **Original Requirement ID & Target**: Refines `REQ-SET-109` (`ATT-7924`), `REQ-SET-105` (`ATT-7918`), `REQ-TRK-084.4`, `REQ-TRK-093` (`ATT-8124`) across `PolarVeritySenseOfflineController.kt`, `PolarH10OfflineController.kt`, and `WorkoutSamplesDatabaseManager.java`.
2. **Historical Origin & Commit Trace**: `ATT-7918` (`patchMissingHeartRateSamples()`), `ATT-7924` (`resolveRecordingAnchorMs()` / `applyBackfillAndCommit()`), `ATT-8124` (H10 UTC epoch anchor).
3. **Root Reason for Existing Formulation**: `ATT-7924` assumed local wall-clock semantics for Polar SDK `LocalDateTime`; `ATT-7918` used unbounded nearest-neighbor `floor`/`ceiling` to absorb ~1 s jitter.
4. **Preservation of Core Invariants**: Preserves gap-only canonical `HR` patching, live HR/GPS/power preservation, `totalRows == 0` empty-table insert path, Verity Sense HRV isolation (`REQ-SET-109.2`), H10 RR-only backfill parity (`intervals.isNotEmpty()`), pinned JVM signatures, and `< 1,500` LoC monolith budgets.
