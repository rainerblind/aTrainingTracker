## 1. Requirements Summary (`REQ-SET-135` — Priority: `High`, Type: `Functional`, Verification: `Unit, Integration`)

| Sub-ID | Normative Contract (SHALL / MUST) |
|---|---|
| `REQ-SET-135.1` | **Extended `AthleteMetricType` & Idempotent Legacy `KEY_HR_MAX` Seeding**: `AthleteMetricType` SHALL add 7 validated enum entries without changing `AthleteMetricsDbHelper.DB_VERSION` (`2`): `HR_MAX_RUN_BPM` (`80..240`), `HR_MAX_BIKE_BPM` (`80..240`), `LTHR_RUN_BPM` (`80..230`), `LTHR_BIKE_BPM` (`80..230`), `LT1_HR_RUN_BPM` (`60..220`), `LT1_HR_BIKE_BPM` (`60..220`), and `LT1_PWR_BIKE_WATTS` (`30..500`). `AthleteMetricType.fromNameOrNull()` SHALL use non-throwing enum lookup (`safeEnumValueOfOrNull`) so `fromCursorBatch()` skips unknown future tokens cleanly. `AthleteMetricsRepository.ensureSeededLocked()` SHALL execute an independent idempotent migration guarded by `KEY_SPORT_HR_MAX_SEEDED` (`sport_hr_max_seeded`, running even when `KEY_ATHLETE_METRICS_SEEDED == true`): when legacy `KEY_HR_MAX` is valid and `HR_MAX_RUN_BPM` / `HR_MAX_BIKE_BPM` lack DB entries, it SHALL seed missing entries atomically in a transaction, project them to `SettingsDataStore`, and set `KEY_SPORT_HR_MAX_SEEDED = true` so subsequent launches never duplicate rows or resurrect deleted entries. |
| `REQ-SET-135.2` | **Sport-Specific `SettingsDataStore` Sync, Non-Blocking Snapshot & Historical Threshold Lookup**: `SettingsDataStore` SHALL define keys `hr_max_run`, `hr_max_bike`, `lthr_run`, `lthr_bike`, `lt1_hr_run`, `lt1_hr_bike`, `lt1_pwr_bike`, reactive `Flow<Int?>` accessors, bounds-clamped suspend setters, and $O(1)$ non-blocking `SettingsSnapshot` fields/sync getters (zero `runBlocking`, `REQ-SET-079`). Legacy `hrMaxFlow` SHALL resolve `max(hr_max_run, hr_max_bike)` falling back to `KEY_HR_MAX`; `setHrMaxRun`/`setHrMaxBike` and `saveCalculatedHeartRateZones` SHALL keep sport keys and `KEY_HR_MAX` atomically consistent. `AthleteMetricsRepository` SHALL project insert/update/delete of all 12 `AthleteMetricType` entries into `SettingsDataStore` (clearing keys when last entry is deleted) and expose `getEffectiveThresholdsAt(sportType: BSportType, timestampMs: Long): EffectivePhysiologicalThresholds` backed by `AthleteMetricsDataSource.getEntryEffectiveAt()`. |
| `REQ-SET-135.3` | **Sport-Specific Historical `hrTSS` & PMC Integration**: `PowerPhysiologyCalculator.calculateHrTss()` and `resolveWorkoutTrainingLoad()` SHALL accept optional `lthrBpm: Double? = null`. When valid `lthrBpm` (`safeHrRest < lthrBpm <= safeHrMax`) is provided, `calculateHrTss()` SHALL normalize 1-hour TRIMP against `thresholdHrr = (lthrBpm - safeHrRest) / (safeHrMax - safeHrRest)` (yielding `hrTSS = 100.0` for 1 hour at `LTHR`). When `lthrBpm` is `null` or invalid, `calculateHrTss()` MUST evaluate `LTHR_HR_RESERVE_FRACTION` (`0.85`) producing bit-for-bit identical results to the legacy formula. `WorkoutTrainingLoadSample` SHALL carry `bSportType: BSportType = BSportType.UNKNOWN` populated from `WorkoutSummaries.B_SPORT` in `WorkoutSummariesDatabaseManager.getWorkoutTrainingLoadRecords()`. `computePerformanceManagementChart()` SHALL accept an optional `thresholdResolver` wired from `AthleteProfileViewModel`'s in-memory `repository.entriesFlow` (recomputing PMC only on physiological threshold changes, preserving zero recomputation on `WEIGHT_KG`/tab toggles). |
| `REQ-SET-135.4` | **Aftermath HRV Threshold Acceptance Persistence & Exhaustive Metric Handling**: `TrackOnMapAftermathViewModel.updateHrZones(newHrvt1, newHrvt2, recalculateZones = true)` and `TrackOnMapScreen` fallback SHALL persist valid `HRVT1` -> `LT1_HR_RUN_BPM`/`LT1_HR_BIKE_BPM` and `HRVT2` -> `LTHR_RUN_BPM`/`LTHR_BIKE_BPM` (by workout `BSportType`) into `AthleteMetricsRepository` (syncing `SettingsDataStore`) alongside optional zone recalculation. `updateFtp(newFtp, lt1PowerWatts = null, recalculateZones = true)` and `HrvThresholdSummaryCard` (`onUpdatePowerThresholds`) SHALL persist `FTP_WATTS` and optional valid `LT1_PWR_BIKE_WATTS` into `AthleteMetricsRepository`. `ZoneSettingsScreen` HR calculator save SHALL persist `HR_MAX_RUN_BPM`/`HR_MAX_BIKE_BPM`. `AthleteProfileScreen` SHALL handle all 12 `AthleteMetricType` values cleanly using 9-locale `strings_athlete_thresholds.xml`. |
| `REQ-SET-135.5` | **`.attbackup` Round-Trip Parity, Forward-Compatibility & Governance Invariants**: Full `.attbackup` backup (`BackupManager`) and restore (`MigrationEngine`) SHALL preserve all 12 `AthleteMetricType` timestamped histories in `AthleteMetrics.db` (v2) and all sport-specific `SettingsDataStore` keys identically across restore. Rows with unknown future `metric_type` tokens SHALL be silently skipped by `getAllEntries()`/`fromCursorBatch()` without crashing. `DataStoreHotPathContractTest`, `TranslationParityTest` (9 locales), `DatabaseSchemaRegistry` (`DB_VERSION = 2`), and `ArchitectureConformanceContractTest` (`SettingsDataStore <= 1,500`, `AthleteProfileScreen <= 1,975`, `WorkoutSummariesDatabaseManager <= 3,148` LoC) MUST pass. |

## 3. Acceptance Criteria (Given-When-Then)

- **Given** an existing user has legacy `KEY_HR_MAX = 188` in `SettingsDataStore` (even with `KEY_ATHLETE_METRICS_SEEDED = true`), **When** `AthleteMetricsRepository` initializes, **Then** `HR_MAX_RUN_BPM = 188` and `HR_MAX_BIKE_BPM = 188` are idempotently seeded in `AthleteMetrics.db` and projected to `SettingsDataStore` with zero duplicates on subsequent launches.
- **Given** an athlete configures `LTHR_RUN_BPM = 172` and `HR_MAX_RUN_BPM = 190` effective `2026-10-01`, **When** `PowerPhysiologyCalculator` computes `hrTSS` for a running workout on `2026-10-15`, **Then** it uses `LTHR = 172` and `HRmax = 190`; when `LTHR` is unset, it preserves the existing 85% HRR result bit-for-bit.
- **Given** an athlete accepts Aftermath HRV thresholds (`HRVT1 = 142 bpm`, `HRVT2 = 168 bpm`) on a cycling workout, **When** `updateHrZones` completes, **Then** `LT1_HR_BIKE_BPM = 142` and `LTHR_BIKE_BPM = 168` are persisted in `AthleteMetrics.db` and reflected in `SettingsDataStore`.
- **Given** an `.attbackup` archive is created after recording all 7 new threshold types and restored onto wiped app state, **When** restore finishes, **Then** all timestamped histories in `AthleteMetrics.db` and current `SettingsDataStore` values match identically, and unknown future enum tokens are safely ignored.
