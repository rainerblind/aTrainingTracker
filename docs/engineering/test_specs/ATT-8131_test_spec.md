## 1. Requirements Summary (`REQ-PER-056` — Priority: `High`, Type: `Functional`, Verification: `Unit, Integration`)

| Sub-ID | Normative Contract (SHALL / MUST) |
|---|---|
| `REQ-PER-056.1` | `PeriodSummariesDatabaseManager` and `PeriodSummaries.db` SHALL be permanently removed from production code and `DatabaseSchemaRegistry` (reducing registered production `SQLiteOpenHelper` subclasses `21 -> 20`). `PeriodsRepository` SHALL hold zero `SQLiteOpenHelper` / `*DatabaseManager` / `WorkoutDataMapper` references (ratcheting `ArchitectureConformanceContractTest.BASELINE_ALLOWED_UI_DB_CALLERS` `22 -> 20`). |
| `REQ-PER-056.2` | `PeriodsRepository.groupedPeriods` SHALL be computed exclusively as a pure, stateless reactive in-memory projection over `WorkoutRepository.allWorkouts` executing on `Dispatchers.Default` (`flowOn(defaultDispatcher)`), filtering strictly `it.finished && it.startTimeS > 0L` and deduplicating via `distinctUntilChangedBy { it.map(WorkoutData::toPeriodProjectionKey) }`. Output SHALL emit `[DAY, WEEK, MONTH, YEAR]` lists sorted by `sortKey DESC` with 100% parity for DST-safe boundaries (`REQ-PER-015`), active-locale labels/date ranges (`REQ-PER-028`), `sportStats` / `DetailedStats` / `LongestWorkout`, spatial bounds & `<= 5` anchors, `regionSummaries` / `primaryRegionSummary` / `<= 8` `polylines` (`REQ-PER-039`, `REQ-PER-046`), empty `workoutIdToPathMap` & `workoutIdToAllPolylinesMap`, `yearlySportContributions` / `dailySportContributions` (`REQ-PER-025`, `REQ-PER-027`), and `extremaMarkers`. `migrationStatus` SHALL emit `null`, and `getWorkoutsForRange(startS, endS)` SHALL serve finished workouts directly from `workoutRepo.allWorkouts.value` sorted by `startTimeS ASC`. |
| `REQ-PER-056.3` | Any finished workout mutation updating `WorkoutRepository.allWorkouts` — including `cropWorkout` (distance/duration/ascent/polyline/bounds change at unchanged workout count), manual metric edit, sport-type change, single/bulk deletion, import, or active-session completion (`finished: false -> true`) — SHALL automatically update Day, Week, Month, and Year `PeriodSummary` totals immediately without imperative sync hooks (`onWorkoutFinished`, `onWorkoutSportChanged`, `onWorkoutDeleted`, `resyncAllPeriods`, `syncPeriodsIfDiscrepancy`, `checkIntegrityAndSync`), while non-period edits (`REQ-PER-016.1`) and 1-Hz unfinished live workout ticks (`REQ-STB-020.3`) SHALL trigger **zero** period recomputations. |
| `REQ-PER-056.4` | App startup (`TrainingApplication.onCreate`) SHALL schedule a one-time asynchronous (`Dispatchers.IO` / background thread) cleanup gated by a fresh preference key (`period_summaries_db_decommissioned_cleaned`) that deletes all obsolete `PeriodSummaries*` files (`PeriodSummaries.db`, `-wal`, `-shm`, `-journal`, and legacy `PeriodSummaries_v*.db*`) from `databases/` without blocking the main thread. Restoring older `.attbackup` archives containing `PeriodSummaries.db` SHALL succeed cleanly (`DatabaseSchemaRegistry.isVersionSupported` accepts unregistered legacy filenames) and `MigrationEngine.performFullRestore` SHALL purge any restored `PeriodSummaries*` files from `databases/` post-swap. |

## 3. Acceptance Criteria (Given-When-Then)

- **Given** historical finished workouts across multiple sports, weeks, months, and years, **When** `PeriodsRepository` emits `groupedPeriods`, **Then** all 4 period levels are computed purely in memory on `Dispatchers.Default` with zero `PeriodSummaries.db` access, preserving exact sums, empty intermediate bar-graph periods, sport breakdowns, contributions, and mini-map metadata.
- **Given** an existing finished workout whose distance, duration, ascent, or sport type is modified via `cropWorkout` or workout edit (keeping total workout count unchanged), **When** `WorkoutRepository.allWorkouts` emits the updated workout, **Then** Day, Week, Month, and Year `PeriodSummary` totals immediately reflect the new values without stale cache artifacts.
- **Given** an existing installation with `PeriodSummaries.db` (`-wal`/`-shm`/`-journal`) on disk (with old `legacy_period_dbs_cleaned = true`) or a legacy `.attbackup` archive containing `PeriodSummaries.db` (v27), **When** app startup cleanup or `.attbackup` restore runs, **Then** restore succeeds without schema downgrade errors and all obsolete `PeriodSummaries*` files are cleanly deleted from `databases/`.
