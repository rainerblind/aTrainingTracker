## 2. Retrospective: In-Depth Analysis of User Feedback

During the sprint, Rainer documented four valuable retro observations directly on ticket [ATT-945](https://rainerblind.atlassian.net/browse/ATT-945). Below is the forensic analysis and countermeasure for each:

### 2.1 Observation 1: Duplicate Sub-Task Creation by Agent vs. Jira Automation
> *"Sometimes, a ticket is created by the agent that is also created by the Jira automation."* — Rainer Blind (2026-09-13T13:20:11.810+0200)

* **Forensic Root Cause**:
  Jira Cloud has automation rules that listen for parent ticket transitions (e.g., transition to `Analysis` triggers generation of `[Analysis] <Summary>`). In some cases, AI agents proactively called `jira_util.py create-subtask` without waiting for the automation or without inspecting `jira_util.py show <Parent>` to check if the sub-task was already created. This produced duplicate sub-tasks (one created by the agent, one by the automation).
* **Corrective Countermeasure**:
  1. **Strict Discovery First**: AI agents SHALL NEVER invoke `create-subtask` immediately after a parent transition.
  2. The agent MUST always run `jira_util.py show <Parent>` to discover the sub-task generated by Jira Automation.
  3. Only if the parent ticket has been in the stage and `show` confirms 0 sub-tasks after verification may the agent create the missing sub-task as a fallback recovery.

---

### 2.2 Observation 2: Inadequate Sub-Task Documentation & Brevity (ATT-955)
> *"ATT-955: No description and very short comment."* — Rainer Blind (2026-09-13T13:37:51.945+0200)

* **Forensic Root Cause**:
  For sub-task ATT-955 (`[Implementation] Workouts that where imported from TCX where not added to the cluster`), the agent posted the comprehensive verification audit report on the parent ticket (ATT-909), leaving the sub-task's `Description` as `None` and writing only a brief 4-line pointer comment on ATT-955. When the human reviewer opened ATT-955 to inspect Gate 4 / Gate 5, the sub-task itself was empty of technical content.
* **Corrective Countermeasure**:
  1. **Sub-Task Self-Sufficiency**: Every sub-task MUST stand on its own. Reviewers approve sub-tasks individually at `Freigabe (Human)`.
  2. **Mandatory Description Population**: The agent MUST write the full stage deliverable (e.g. Implementation Report, modified files, architectural rationale, verification results) directly into the sub-task's `Description` via `jira_util.py update-desc`.
  3. **Comprehensive Audit Comment**: The Agent 2 review comment must provide self-contained, concrete audit findings directly on the sub-task, not merely redirect to the parent ticket.

---

### 2.3 Observation 3: Empty Ticket at Time of Review Transition (ATT-961)
> *"TT-961: Nothing at all. 😞"* — Rainer Blind (2026-09-13T14:05:37.549+0200)

* **Forensic Root Cause**:
  A race condition in agent tool execution ordering. The agent moved ATT-961 to `In Überprüfung` / `Freigabe (Human)` BEFORE populating the ticket Description. When Rainer received the notification and opened the ticket, it was completely blank.
* **Corrective Countermeasure**:
  1. **Enforce Strict Execution Sequencing**:
     $$\text{Step 1: Write Description} \longrightarrow \text{Step 2: Post Comment} \longrightarrow \text{Step 3: Transition State}$$
  2. An agent is strictly forbidden from transitioning a sub-task to `In Überprüfung` or `Freigabe (Human)` until `update-desc` has successfully executed and verified.

---

### 2.4 Observation 4: Finalizing Feature/Bugfix Branches in Git
> *"Necessary Imporvement: Always finish the bug/feature in git when the ticket is finished."* — Rainer Blind (2026-09-13T14:11:56.438+0200)

* **Forensic Root Cause**:
  During ATT-956, all Jira sub-tasks were approved and closed, but the git branch `bugfix/ATT-956` was left open and unmerged on the workstation. Rainer had to manually merge `bugfix/ATT-956` into `develop` (`864c1aa7`).
* **Corrective Countermeasure**:
  1. Once Stage 5 is approved and the ticket is ready for completion, the agent MUST autonomously checkout `develop` and execute a non-fast-forward merge:
     ```bash
     git checkout develop
     git merge --no-ff -m "Merge branch '<branch>' into develop" <branch>
     ```
  2. Verify clean git working tree (`git status`).
  3. Post an integration comment on the parent ticket documenting the merge commit hash.
  *(This was practiced flawlessly on all subsequent tickets: ATT-896, ATT-911, ATT-883, ATT-917, ATT-987, and ATT-993).*

## 3. Workflow Hardening & Protocol Updates

To institutionalize these lessons learned permanently, the following concrete additions are made to `docs/project_protocol.md`:
1. **Rule on Automated Sub-Task Discovery**: Never create sub-tasks manually unless explicitly confirmed missing.
2. **Rule on Sub-Task Self-Sufficiency**: Every sub-task must contain its complete deliverable in its `Description`.
3. **Rule on Execution Order**: Description and Comments MUST precede state transitions.
4. **Rule on Git Finalization**: Every completed ticket must be merged into `develop` with `--no-ff` and integration comment posted before proceeding.
