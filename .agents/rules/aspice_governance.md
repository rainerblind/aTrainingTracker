## Rule 1: Obey the Rules, Two-Tier Context Refresh & Constructive Resistance
* **Ticket Start / Ceremony Start / Post-Compaction Resume**: Before starting a new ticket, starting a sprint ceremony, or resuming after a context compaction, explicitly read `.agents/rules/aspice_governance.md` and the relevant domain standard (`docs/design_guidelines.md` for UI tickets, `docs/coding_standards.md` for logic/service/DB tickets) via `view_file`.
* **Intra-Ticket Stage Transitions (Stages 1 $\rightarrow$ 2 $\rightarrow$ 3 $\rightarrow$ 4 $\rightarrow$ 5)**: Whenever `tools/jira_util.py` transitions a parent ticket into a lifecycle stage (via `move <KEY> analysis` or `gate-verdict <SUBTASK> PASS`), it **automatically prints** the target stage's `SKILL.md` and core governance rules to `stdout`, eliminating separate manual `view_file` turns between stages unless a context compaction occurred.
* **Constructive Resistance & Documented Deviations (*Pflicht zum Widerspruch & Dokumentierte Abweichungserlaubnis*)**: Agents MUST NOT initiate shortcuts. When the human user requests an exception from standard process, the agent SHALL first offer constructive resistance (explaining the guardrail's purpose and associated risk). If the human insists, the exception, its rationale, and exact changes MUST be cleanly documented in Jira and the deliverable/walkthrough.

## Rule 2: Autonomous Full-Sprint Execution, PO Model-Switch Checkpoints, Just-In-Time `Analysis` Transition & Mid-Sprint Ticket Additions
* **PO Coordinator Model-Switch Checkpoints at Phase Boundaries (`Rule 81` — `ATT-6289`)**: The human Product Owner manually switches the top-level Coordinator model across the 3 sprint phases (**Planning / Ceremony 1**: `Argon` or `Carbon`; **Main Execution / Phase 2 Coordinator**: `Flash`; **Review & Retro / Ceremony 2**: `Gemini 4 Carbon`). Therefore:
  1. **End of Ceremony 1 $\rightarrow$ Start of Phase 2 Checkpoint**: Once all Ceremony 1 sprint tickets are audited and open questions resolved, the Coordinator **MUST pause once** with an explicit handoff prompt: *"Ceremony 1 Planning complete. Please switch the Coordinator model to `Flash` and reply `start` to launch autonomous Phase 2 execution."* Do **NOT** launch Phase 2 subagents while still in the Ceremony 1 Planning turn on `Argon`/`Carbon`.
  2. **Inside Phase 2 (100% Uninterrupted Autonomous Execution on `Flash`)**: Once the user switches to `Flash` and starts Phase 2, execute the entire active sprint backlog (`ORDER BY rank ASC`) continuously from ticket to ticket across Stages 1–5 (with persistent `subagent_pro` explicitly set to `Model: "pro"` and `subagent_flash` set to `Model: "flash"` per Rule 7) **without pausing or asking the user whether to continue**.
  3. **End of Phase 2 $\rightarrow$ Start of Ceremony 2 Checkpoint**: After all sprint tickets reach `Final Review (Human)` AND the Tier 2 Sprint Integration & CI Static-Analysis Gate + `./gradlew installDebug` succeed on `sprint/<SPRINT_NAME>`, stop and prompt the PO: *"Phase 2 and Tier 2 Gate complete (100% green). Please switch the Coordinator model to `Gemini 4 Carbon` to begin Ceremony 2 (Sprint Review & Retro)."*
* **Just-In-Time Transition to `Analysis` (`Rule 78` — `ATT-5829`, `"Tickets sollten von den Agenten erst dann nach Analyse geschoben werden, wenn die Analyse startet."`)**: Never batch-move all sprint tickets to `Analysis` at Sprint-Start (Ceremony 1). Keep sprint tickets in `Zu erledigen` and transition a ticket to `Analysis` (`python3 tools/jira_util.py move <KEY> "analysis"`) **only when Stage 1 (`[Analysis]`) actually begins for that specific ticket**.
* **Automatic Realization of Tickets Added to an Already-Started Sprint (`Rule 65` — `ATT-4776`, `"When a new ticket is added to the sprint when the sprint is already started. Please realize this ticket."`)**: Because only the human user can add tickets to an active sprint, any ticket added by the human user into an already-started sprint during Phase 2 (`status = 'Zu erledigen'`, excluding `Review & Retro`) carries implicit human approval. Before concluding Phase 2, always re-query the active sprint for any remaining or newly added `Zu erledigen` tickets, move each one to `Analysis` (`python3 tools/jira_util.py move <KEY> "analysis"`) as its Stage 1 starts, and execute Stages 1–5 autonomously without pausing or asking for confirmation.
* When resuming from a context compaction, never treat the compaction summary's "Next Steps" as a question for the user—immediately query Jira / git state and resume execution autonomously.

## Rule 3: Human Decision Gate on Parent Tickets & Synchronous Stage Progression
* **Parent Tickets**: Moving any parent ticket to `Erledigt` is reserved **exclusively** for the human user. Agents always end parent tickets at `Final Review (Human)` (assigned to `human`).
* **Sub-Tasks**: Stage sub-tasks that pass Gate 1–5 audit close directly to `Erledigt` via `python3 tools/jira_util.py --as agent2 gate-verdict <SUBTASK_KEY> PASS "<Audit Report>"`, which synchronously advances the parent ticket to the next stage column (`Test Spec` $\rightarrow$ `Implementation Plan` $\rightarrow$ `Implementation` $\rightarrow$ `Test` $\rightarrow$ `Final Review (Human)`).

## Rule 4: Code Lock Until Gate 3 Passes
* Before creating or modifying any production source code in `app/src/...` during Stage 4, run:
  ```bash
  python3 tools/jira_util.py check-gate <Impl-Plan-Subtask-Key>
  ```
  and confirm exit code `0` (`GATE_PASSED`). If Gate 3 is not `Erledigt`, production code edits are strictly blocked.

## Rule 5: Ticket Creation Stops Immediately
* When asked to create a backlog or follow-up ticket (`python3 tools/jira_util.py create-issue ...`, which automatically ranks it at the top of the backlog), report the new issue key and **STOP IMMEDIATELY**. Never branch, spawn sub-tasks, or start implementation unless explicitly instructed.

## Rule 6: Unattended Escalation via Jira
* If a requirement ambiguity or design decision blocks a sub-task mid-sprint, never block the console:
  1. `python3 tools/jira_util.py comment <SUBTASK_KEY> "Question for Human: ..."`
  2. `python3 tools/jira_util.py assign <SUBTASK_KEY> human`
  3. Immediately continue with the next unblocked ticket in the sprint backlog.

## Rule 7: Asymmetric `pro` / `flash` Zipper Principle & Epic-Scoped Persistent Ping-Pong Subagents
* **Epic-Scoped Persistent Subagent Pairs & Concurrent Background Pre-Warming of `agent2` (Rules 61 & 63 — `ATT-4520`, `ATT-4670`)**: Maintain a dedicated pair of persistent `self` subagents (`invoke_subagent` with `TypeName: "self"`) per **Parent Epic** across the sprint (`epic_agents[epic_key] = (pro_id, flash_id)`), or per ticket when a ticket has no Parent Epic:
  * `subagent_pro` (`Model: "pro"`, `Role: "ATT-XXXX / Epic Pro Agent"`)
  * `subagent_flash` (`Model: "flash"`, `Role: "ATT-XXXX / Epic Flash Agent"`)
  * **Create `agent2` (`subagent_flash`) at the Start in the Background (`Rule 63` — `ATT-4670`)**: When starting the first ticket of an Epic (or a standalone ticket) at Stage 1, launch **both** `subagent_pro` and `subagent_flash` concurrently in the initial `invoke_subagent(Subagents=[...])` call:
    1. `subagent_pro` executes **Stage 1 Doing (`[Analysis]`, `--as agent1`)**.
    2. `subagent_flash` (`agent2`) pre-warms its context in the background during Stage 1 (reading `.agents/rules/aspice_governance.md`, `docs/coding_standards.md` / `docs/design_guidelines.md`, `.agents/skills/stage2-req-test-spec/SKILL.md`, and `python3 tools/jira_util.py show <KEY>` + inspecting the relevant target files) and then waits idly for the Coordinator's `send_message` with the Stage 1 subtask key. Because `subagent_pro`'s Stage 1 analysis takes longer than `subagent_flash`'s context warm-up, `subagent_flash` enters Gate 1 + Fused Stage 2 Doing with zero cold-start latency.
  * **When a subsequent ticket in the sprint belongs to an Epic that already has a warm `(subagent_pro, subagent_flash)` pair**, dispatch Stage 1 and all subsequent fused zipper turns to that existing pair via `send_message` instead of spawning new subagents, eliminating cold-start overhead and preserving deep domain context across related tickets.
  * **Proactive 3-Ticket Rotation & Subagent Error / Timeout Replacement (`Rules 62 & 65` — `ATT-4596`, `ATT-4776`)**: When an Epic has $\ge 4$ tickets in a sprint, proactively rotate (kill and respawn) the Epic-scoped `(subagent_pro, subagent_flash)` pair after every **3 completed tickets** to prevent accumulated multi-ticket context from hitting `INVALID_ARGUMENT (code 400)`. If a persistent subagent enters an `errored` state or hits a `context deadline exceeded` timeout mid-ticket, terminate that specific subagent (`manage_subagents(Action="kill")`), spawn a fresh replacement of the same model tier for that Epic slot, and dispatch the current stage prompt to the replacement.
* **Context-Warm Ping-Pong via `send_message`**: Reuse their `conversationId`s across all 5 stages via `send_message`, swapping their roles (`--as agent1` Doing vs. `--as agent2` Gate Review) on every stage so no model tier audits its own tier and each subagent enters its Doing turn already warm from auditing the previous Gate:

| :--- | :---: | :---: | :--- |
| **Stage 1: Analysis** (`[Analysis]` $\rightarrow$ Gate 1) | **`subagent_pro`** | **`subagent_flash`** *(pre-warmed in background)* | `subagent_flash` audits Gate 1 (`--as agent2`) and **immediately executes Stage 2 Doing (`--as agent1`) in the same turn** upon `PASS` |
| **Stage 2: Req & Test Spec** (`[Req & Test Spec]` $\rightarrow$ Gate 2) | **`subagent_flash`** *(fused with Gate 1)* | **`subagent_pro`** *(via `send_message`)* | `subagent_pro` audits Gate 2 (`--as agent2`) and **immediately executes Stage 3 Doing (`--as agent1`) in the same turn** upon `PASS` |
| **Stage 3: Implementation Plan** (`[Impl-Plan]` $\rightarrow$ Gate 3) | **`subagent_pro`** *(fused with Gate 2)* | **`subagent_flash`** *(via `send_message`)* | `subagent_flash` audits Gate 3 (`--as agent2`) and (for Standard tickets) **immediately executes Stage 4 Doing (`--as agent1`) in the same turn** upon `PASS` |

* **Reactive Turn Boundaries & Hub-and-Spoke Topology (Strictly One Subagent Dispatch per Turn, Zero Peer-to-Peer `send_message`, Rules 56, 61, 63 & 64)**: `invoke_subagent` or `send_message` **MUST** be the final tool call of the Coordinator's turn (followed only by the single Rule 66 watchdog `schedule`)—immediately stop calling tools to end the turn and wait for the `<SYSTEM_MESSAGE>` containing the newly created Jira subtask key. Subagents **MUST** strictly report back to the Coordinator at the end of their turn and **NEVER** send peer-to-peer `send_message` calls directly to another subagent (`ATT-4718`). Never call `manage_subagents(Action="list")` or `manage_task(Action="status")` after `send_message`, never send a Gate Review `send_message` to the second subagent in the same turn as the Doing `send_message`, and never call `schedule` timers in a polling loop.
* **Lost-Wakeup Watchdog & Coordinator Ownership (Rule 66 — `ATT-4864`, `"Warum wurde das erste Ticket nicht komplett selbstständig abgearbeitet?"`)**: Subagent reports can fail to wake the Coordinator (Sprint 2026-44.1: the Stage 1 report of `ATT-4843` stayed undelivered and Phase 2 stalled until the human typed "continue" into the *subagent's* tab, which then acted as Coordinator). Therefore:
  1. Directly after each dispatch (`invoke_subagent` / `send_message`), the Coordinator sets **exactly one** watchdog timer with `schedule(DurationSeconds=1200, TimerCondition=<dispatched subagent id>, Prompt="Watchdog: verify Jira/git state of <KEY> and resume")` as the final tool call. A timely subagent message cancels it; if it fires, re-derive the state from Jira (`jira_util.py show <KEY>`) and git and re-dispatch or continue. This single per-dispatch watchdog is not polling.
  2. While any regular sprint ticket is not yet in `Final Review (Human)`, a Coordinator turn **MUST NOT** end with only a status report — it ends with a dispatch + watchdog.
  3. Subagents never take over the Coordinator role. If a human instruction arrives in a subagent's conversation, the subagent completes only its own stage, reports to the Coordinator, and tells the human which conversation is the Coordinator.
* **Subagent Cleanup**: Terminate standalone ticket subagents once squashed onto `sprint/<SPRINT_NAME>`, and terminate Epic-scoped subagent pairs once all sprint tickets in that Epic are complete (`manage_subagents(Action="kill", ConversationIds=[...])` or `kill_all`).

## Rule 9: Parallel Sprint Execution Across Disjoint Epics (`REQ-PRO-041` — `ATT-5914`, `Rule 81` — `ATT-6289`)
* **Strict Concurrency Bounding & Disjoint Epics Only (`REQ-PRO-041.1`, `Rule 81` — `ATT-6289`)**: The Coordinator MAY dispatch up to three tickets concurrently (`concurrency = 3`) ONLY when the tickets belong to completely disjoint Parent Epics with zero package and zero living-doc shard overlap (preferring at most 1–2 UI-touching Epics alongside Backend/Service/DB/Process Epics). Concurrent execution within the same Epic is strictly prohibited.
* **Worktree Isolation via `Workspace: "share"` & Submodule/Branch Hygiene (`REQ-PRO-041.1`, `Rule 81` — `ATT-6318`, `ATT-6289`)**: Persistent subagent pairs for parallel tickets MUST be spawned using `Workspace: "share"`, ensuring each pair operates in an isolated Git worktree backed by the shared repository without branch checkout collisions or dirty tree overwrites. Subagents in `Workspace: "share"` worktrees **MUST NEVER** create filesystem symlinks at submodule paths (`ANT-Android-SDKs`) or stage them via `git add -A` (which overwrites the `160000` submodule gitlink with a `120000` symlink), and MUST run `git checkout --detach` in sibling worktrees before `git branch -D feature/<KEY>` so no stale `feature/*` branches remain.
* **POSIX `flock` Mutual Exclusion (`REQ-PRO-041.2`, `/tmp/att_build_merge.lock`)**: Heavy resource operations and shared physical-device (`adb`) deployments MUST be serialized using `python3 tools/parallel_sprint_lock.py <command>` (or `tools/locked_build_merge.py`):
  1. Unit test execution: `python3 tools/parallel_sprint_lock.py ./gradlew testDebugUnitTest ...`
  2. Physical device deployment & ADB screenshot capture (when $>1$ UI lane is active): `python3 tools/parallel_sprint_lock.py bash -c "./gradlew installDebug && adb ..."`
  3. Stage 5 living documentation index synchronization and squash-merges onto `sprint/<SPRINT_NAME>`:
     `python3 tools/parallel_sprint_lock.py git rebase origin/sprint/<SPRINT_NAME> && python3 tools/verify_requirement_governance.py --sync-indexes && git merge --squash feature/<KEY>`
* **Domain-Partitioned Localization (`REQ-PRO-041.3`)**: String resources MAY be partitioned into `app/src/main/res/values*/strings_<domain>.xml` to prevent end-of-file merge conflicts during concurrent additions. `TranslationParityTest.kt` dynamically discovers all `strings*.xml` across all 9 locales.
* **Deterministic Living Docs Recalculation (`REQ-PRO-041.4`)**: Whenever a parallel branch rebases onto `sprint/<SPRINT_NAME>`, execute `python3 tools/verify_requirement_governance.py --sync-indexes` under the merge lock prior to squashing.
